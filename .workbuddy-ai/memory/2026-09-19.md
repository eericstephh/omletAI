# 2026-09-19 — AICreatorStudio

## Fixed: adjustment sliders (Brightness/Contrast/Saturation) never changed the video

**Symptom (user report, Persian):** on the editor screen the bottom "Adjustment"
toolbar's sliders move their label and thumb, but the video image never changes.

**Root cause — a third-party API *shape* assumed rather than verified.**
`export/GradeRgbMatrix.kt` is the single Media3 `RgbMatrix` implementation shared
by the preview (`EditorScreen.kt:1683-1690`, via `ExoPlayer.setVideoEffects`) and
the export (`VideoExportEngine.kt:681`). It returned the app's raw 4×5 row-major
`ColorMatrix` (20 floats, offsets in 0..255).

Media3 1.5.0 requires a **4×4 column-major matrix of exactly 16 floats** with
offsets in 0..1. Verified from `media3-effect-1.5.0-sources.jar` and the shipped
GLSL assets:
- `RgbMatrix.getMatrix` KDoc: "Returns the 4x4 RGB transformation matrix".
- `DefaultShaderProgram.updateMatrixCache`:
  `checkState(newMatrix.length == 16, "A 4x4 transformation matrix must have 16 elements")`
  — the length check sits inside the `!Arrays.equals(cache, new)` branch, so a
  20-element array never matches the 16-element cache and the assertion fires on
  the **first frame**.
- It is reached from `drawFrame` (~line 506) **outside** the `try` block, so it
  propagates as an `IllegalStateException` to
  `VideoFrameProcessingTaskExecutor.handleException`, which sets
  `shouldCancelTasks = true` and reports the error — **cancelling the entire video
  pipeline**, in the preview and the export alike.
- `fragment_shader_transformation_es2.glsl`:
  `gl_FragColor = uRgbMatrix * vec4(inputColor.rgb, 1)` — normalised 0..1 colour,
  hence the ÷255 rescale and the constant term living in column 3.

The false assumption was written down as fact in **two** KDoc blocks:
`ColorGradingMath.fullExportMatrix` ("the same layout `android.graphics.ColorMatrix`
and Media3's `RgbMatrix` both consume") and the `VideoExportEngine` comment at
~line 1560 ("Media3's `RgbMatrix` interface accepts a raw 4×5 row-major matrix").
Both corrected in place. **Comments are intent, not fact** — third time that rule
has paid off here.

**Fix (one file, zero call-site changes):** `export/GradeRgbMatrix.kt` keeps the
4×5 as its public input (the `matrix` setter, so both existing call sites are
untouched) and converts to 4×4 column-major on assignment via a new pure,
unit-tested top-level function `toMedia3RgbMatrix4x4`; `getMatrix` returns the
cached 16-float array — still `@Volatile`, still one reference swap per slider
tick, no per-frame allocation.

**Tests:** new `app/src/test/java/com/aicreatorstudio/app/export/GradeRgbMatrixTest.kt`,
7 tests, all green: identity conversion, rejection of a non-4×5 input, column-major
transposition, the ÷255 offset rescale, the 16-float invariant on the effect
itself, the live-preview matrix swap, and a neutral grade reducing to Media3's
identity. They are *guards*, not reproductions — a JVM test cannot load
`DefaultShaderProgram` or execute GL, so `length == 16` is asserted against
Media3's documented contract.

**Honest caveat:** the defect applied to the **export** as well, since both
renderers share the object. The 2026-09-10 "export color parity" claim rested on
matrix-arithmetic unit tests that never build an effect or execute GL, so the
export grade was inert too. Both paths still need a **device smoke test** to
confirm — unit tests structurally cannot verify that GL composites as expected.

## Round 2 (same day) — two more "I move the control and nothing changes" regressions

After the grade fix the user said "continue", so I audited the *rest* of the same bug
class: every other hand-written Media3 effect, plus the preview/export effect lists.

**Audit result: no second contract violation.** `SharpnessEffect` (a
`SeparableConvolution`), `VignetteOverlay` (`BitmapOverlay`), `GrainEffect` (custom
`GlShaderProgram`), `CanvasBackgroundOverlay`, `ClipMotionMatrixEffect`,
`ClipMotionBlurEffect`, `ClipMotionWashOverlay` and `SubtitleWindowOverlay` all pass the
static checks against the real Media3 sources: no array-length mismatch against a
`checkState`/`checkArgument`, correct `configure` sizes, overlay scales derived from the
*bitmap* rather than the frame, no undeclared uniform, and every `release()` either calls
`super` or deletes its GL program. `ClipMotionMatrixEffect` returns `FloatArray(16)`, which
is what `DefaultShaderProgram`'s shared 16-float assertion requires — so it was never at
risk of the `GradeRgbMatrix` failure.

**Fixed — the preview attached only the grade effect.** `EditorScreen.kt`'s effect list held
`gradeEffect` alone, so `SharpnessEffect` / `VignetteOverlay` / `GrainEffect` were never
instantiated for the live pipeline: the Detail / Vignette / Grain sliders moved the panel
and changed the exported file but changed nothing on screen. Their own KDocs
(`SharpnessEffect.kt:20-31`, `VignetteOverlay.kt:23-32`, `GrainEffect.kt:47-55`,
`SharpnessKernel.kt:18-20`) and `ColorGradingMath`'s class KDoc all assert
"preview == export", and `2026-09-17.md:189-190` records the preview **did** have
`grainEffect` + `effectSignature` bit 8 — so this was a **regression, not a design
choice**. Restored with one long-lived `remember`ed instance per effect whose mutable
`@Volatile` field is rewritten per recomposition (no pipeline rebuild on a value change);
membership is decided by the **same pure predicates the export uses**
(`SharpnessKernel.isActive` / `VignettePlate.isActive` / `GrainSignal.isActive`) and folded
into `effectSignature` bits 1/2/4/8, so a membership change rebuilds the pipeline while a
slider drag does not. Order mirrors the export: grade → sharpness → vignette → grain. The
vignette is a `TextureOverlay`, which is **not** an `Effect`, so it is wrapped in one
long-lived `OverlayEffect`.

**Fixed — the blurred canvas background.** `EditorScreen.kt`'s Layer 1 had regressed to
`PlayerView(ctx)` (default `SurfaceView`), so `Modifier.blur(36.dp)` acted on a transparent
hole and the "blur" background was a sharp ZOOM-cropped copy. Restored the
`R.layout.player_view_texture` inflate that Layer 2 uses (the 2026-09-17 fix). Note the
residual: `Modifier.blur` is a no-op below API 31 regardless of surface type.

**The transferable lesson:** the preview's effect list is the **single chokepoint where
preview/export parity is decided**, and it fails *silently and totally* — an effect missing
from that one list is invisible on screen while still working in the file. It is 4 lines in
the middle of a 4900-line Compose file with no test covering it. Bug class #1's "grep for
the consumers" rule finds a field with *no* consumer; it does **not** find a field whose
consumer exists but was dropped from a list. **When several features claim "preview ==
export" in their KDocs, diff the two effect lists against each other** — that is the check
that would have caught both of these.

**Verification status:** `testDebugUnitTest` compiles clean and is byte-identical to before
(1189 tests, the same 5 pre-existing Whisper failures, 2 skipped). The preview changes are
**compile-verified only** — unit tests structurally cannot exercise GL, so all three fixes
still need a device smoke test.

Also found: `animT` uses a raw `%` instead of clamping to the clip window; the black/white
flash `Box`es `ClipMotionEffects.kt` refers to ("EditorScreen, layer 2.4") **do not exist**;

1. **Audio fades were export-only.** `StemClip` declares `fadeInMs`/`fadeOutMs` and

2. **The Layer 2.5 colour overlay was dead code.** An empty `Box` with

   (which includes the SurfaceView beneath it)") corrected in place with a warning not to
   re-add a View-level colour filter — the foreground player is now a TextureView, so a

"this is all fixed", re-derive it; a claim of completeness is the least reliable kind.

## Round 4 — the preview *still* didn't change on device: the sink gate

The user tested on a real phone and reported the **same** symptom after the `GradeRgbMatrix`
16-float fix: the adjustment sliders move the number and the thumb, and not one pixel
changes. They asked five specific questions and forbade any restructuring.

### What the trace actually proved

I read the Media3 1.5.0 sources out of
`~/.gradle/caches/modules-2/files-2.1/androidx.media3/*/1.5.0/*-sources.jar` rather than
guessing. **Everything upstream of the renderer is correct:**

- `ExoPlayerImpl.setVideoEffects` has **no** timeline check in 1.5.0 — it only does a
  `Class.forName("androidx.media3.effect.PreviewingSingleInputVideoGraph$Factory")` +
  `getConstructor(VideoFrameProcessor.Factory.class)` probe (both exist) and then
  `sendRendererMessage(TRACK_TYPE_VIDEO, MSG_SET_VIDEO_EFFECTS, effects)`.
- `ExoPlayerImpl.sendRendererMessage` iterates `renderers`, which is a `Renderer[]` built in
  the `ExoPlayerImpl` **constructor** (line 268, `checkState(renderers.length > 0)`) — so the
  video renderer is reachable from the moment the player exists.
- `ExoPlayerImpl.createMessageInternal` passes `internalPlayer.getPlaybackLooper()` as the
  message's default looper, and `PlayerMessage`'s `positionMs` defaults to `C.TIME_UNSET`
  (line 107), so `sendMessageInternal` takes the *immediate delivery* branch →
  `sendMessageToTarget` → `deliverMessage` → `renderer.handleMessage(...)`.
- Ordering is safe: `setMediaItem`/`playWhenReady`/`setVideoEffects`/`prepare`/`seekTo` all
  post onto the same playback handler, and `MSG_SEND_MESSAGE` is posted before `MSG_PREPARE`.
- `getSurfaceForCodec` returns `videoSink.getInputSurface()` when a sink exists, so the
  decoder feeds the VideoGraph.
- `PlaybackVideoGraphWrapper.getSink()` always returns the `InputVideoSink` (never the
  `DefaultVideoSink`, whose `setVideoEffects` just throws `UnsupportedOperationException`).
- `InputVideoSink.setVideoEffects` dedupes on `videoEffects.equals(...)`, then
  `setPendingVideoEffects` → `maybeRegisterInputStream` → `videoFrameProcessor.registerInputStream(...)`
  (which no-ops harmlessly while `inputFormat == null` and picks the effects up when the
  format arrives).

### The actual gate

```java
// MediaCodecVideoRenderer.onEnabled (lines 697-705)
if (!hasSetVideoSink) {
  if (videoEffects != null && videoSink == null) {
    videoSink = new PlaybackVideoGraphWrapper.Builder(context, videoFrameReleaseControl)...
  }
  hasSetVideoSink = true;
}
// MediaCodecVideoRenderer.setVideoEffects (lines 1223-1227)
videoEffects = effects;
if (videoSink != null) { videoSink.setVideoEffects(effects); }
```

`grep "videoSink = "` over the whole renderer returns **exactly one** assignment: line 434,
in the constructor. `onReset()` sets `hasSetVideoSink = false` but does **not** null the
sink, and nothing anywhere creates one later. So:

> **If the first `onEnabled` runs before anyone has called `setVideoEffects`, the sink is
> never created and every effect is silently discarded for the entire life of the player.**

The symptom is then *exactly* the bug report — the video plays normally (the decoder renders
straight to the `displaySurface` because `videoSink == null`), the sliders and the matrix are
all correct, and not one pixel changes. It reads like a UI wiring bug and it is not.

### Fixes (three small edits, no restructuring)

1. **`EditorScreen.kt`, player builder** — added `setVideoEffects(emptyList())` inside the
   `remember { ExoPlayer.Builder(...).build().apply { ... } }` block. This is the earliest
   moment the player exists, so `videoEffects != null` is guaranteed for the first
   `onEnabled` however the editor is entered. Legality verified against the source:
   `setVideoEffects` needs no media item in 1.5.0, and `createMessageInternal` guards the
   unset window index (`currentWindowIndex == C.INDEX_UNSET ? 0 : ...`).
2. **`EditorScreen.kt`, media-item effect** — kept as a second line of defence, with the
   comment corrected to say why (the previous comment claimed `prepare()` alone was the
   trigger).
3. **`EditorScreen.kt`, preview effect list** — the grade pass is now **always** in the list
   (`effects += gradeEffect`), even for an identity matrix, and `useGrade` /
   `effectSignature` bit 1 are gone. Reason: the old `!isIdentityMatrix(...)` gate made the
   *first* slider movement a change of list **membership**, which Media3 answers with
   `registerInputStream` + a graph rebuild/flush — while a *value* change needs no rebuild at
   all, because `RgbMatrix.getMatrix()` is re-queried per frame on the GL thread. With the
   instance permanently in the list, `InputVideoSink`'s `equals` dedup even short-circuits, so
   a drag only swaps `gradeEffect.matrix`. An identity through `uRgbMatrix * vec4(rgb, 1)` is
   a no-op, so always-on costs one mat4 multiply per pixel. The export still skips identity.

Also: the bare `runCatching { player.setVideoEffects(effects) }` now logs on failure instead
of swallowing it — a swallowed failure here *is* the symptom.

### Answers to the user's five questions (all evidence-backed)

1. `GradeRgbMatrix` is **not** export-only — the preview builds the same class and passes it
   to `player.setVideoEffects`. The break was one layer further down, at the renderer.
2. The editor uses `PlayerView`, inflated from `R.layout.player_view_texture`
   (`app:surface_type="texture_view"`), bound to the single `remember`ed `exoPlayer`.
3. Yes — `player.setVideoEffects(effects)` is called on that same instance. The problem was
   *when*, not *which*.
4. `PlayerView`'s surface type is irrelevant to `setVideoEffects` (Media3 applies effects in
   the renderer, before the frame reaches the Surface); `TextureView` only matters for
   Compose-level effects that must *read* the pixels (`Modifier.blur`, `saveLayer`).
   `GlObjectsProvider` needs no configuration — `PlaybackVideoGraphWrapper` builds its own
   `DefaultVideoFrameProcessor.Factory` via `ReflectiveDefaultVideoFrameProcessorFactory`.
5. The chain is cut at `MediaCodecVideoRenderer.setVideoEffects`'s `if (videoSink != null)`.

**Gate:** `testDebugUnitTest` = 1189 tests, same 5 pre-existing Whisper/asset failures,
2 skipped — identical to baseline. Compile-verified only; GL cannot be unit-tested.

**Separate parity bug found while tracing (NOT fixed, not the reported symptom):**
`EffectPresets.bcsMatrix` (preview) and `ColorGradingMath.fullExportMatrix` (export) compute
B/C/S with *different* maths — preview is `scale=contrast`, `offset=(brightness-1)*128`;
export is `k = c*b*s`, `off = 127.5*(1-c)*b`. So the preview and the MP4 disagree on
brightness/contrast/saturation. Worth fixing, but it makes the picture differ, not stay
identical, so it cannot be the reported bug.

### Round 4b — the "one-shot gate" sweep, and closing the observability hole

Once bug class #4 was identified, the same pattern had to be ruled out everywhere else in
the preview link. Method: for each long-lived effect instance, find the Media3 code that
decides whether to **re-read** its mutable state, and check the answer is "every frame".

- `GradeRgbMatrix` — `DefaultShaderProgram.updateCompositeRgbMatrixArray` calls
  `rgbMatrices.get(i).getMatrix(presentationTimeUs, useHdr)` **per frame** (line 665).
  ✓
- `SharpnessEffect` — `SeparableConvolutionShaderProgram` line 262 calls
  `convolutionFunction1DProvider.getConvolution(presentationTimeUs)` per frame, then
  `if (!currentConvolutionFunction.equals(lastConvolutionFunction)) updateFunctionTexture(...)`.
  **This is a gate**: a `ConvolutionFunction1D` that does not override `equals` would be
  identity-equal to itself forever and the kernel LUT would never be re-uploaded — the
  Detail slider would be dead after the first frame. `SharpeningFunction` **does** override
  `equals` by `weight` and `getConvolution` returns a fresh instance when the weight
  changes, so it is correct. ✓ (Also worth noting: `DefaultVideoFrameProcessor.configureEffects`
  has the same shape — `if (forceReconfigure || !activeEffects.equals(...))`.)
- `VignetteOverlay` — `getTextureId` is re-queried per frame by the overlay program and the
  plate cache is keyed on the whole `grading`, so a grade change regenerates it. ✓
- `GrainEffect` — custom `BaseGlShaderProgram`; `drawFrame` reads `effect.grain` and sets the
  uniforms per frame. ✓
- `AudioMixerPlayer` — creates one player per wanted stem inside `update()`, so a newly added
  audio clip gets its own player; no gate. ✓

**Result: no other instance of the class in the preview link.** The always-on grade change
is therefore consistent with how the other three effects already behaved, not a special case.

**The observability hole (fixed).** Both round-4 device tests were inconclusive for one
reason: **nothing in the app listened for `Player.onPlayerError`.** When the GL pipeline
dies, `MediaCodecVideoRenderer` parks a pending `PlaybackException`, the picture freezes on
its last frame, and the editor is indistinguishable from "the slider is not wired up" —
which is exactly what the 20-float matrix assertion did in round 3, and it reported a hard
error into the void. Added a `DisposableEffect(exoPlayer)` that logs
`onPlayerError` with `errorCodeName` + message under tag `EditorScreen`. No behaviour change.

**Gate:** `testDebugUnitTest` = 1189 tests, same 5 pre-existing failures, 2 skipped.
Existing `GradeRgbMatrixTest` cases already pin the two invariants the always-on grade
relies on: `a neutral grade converts to Media3's identity so the shader is a no-op` and
`assigning a matrix changes what the next frame reads`.

**Lesson for the skill:** a third-party effect API almost always has *one* place where it
decides whether to re-read your state. Find it, and check the answer is "every frame" — an
`equals`-based cache in the third party is indistinguishable from a broken slider.

## Round 5 — closing the last unproven hop: does the paused-state seek actually re-render?

The only hop left unverified after round 4b was the *paused-state invalidation* at the end
of the preview effect `LaunchedEffect`. The preview runs with `playWhenReady = false` and
sits at `STATE_READY`, and no new frame is produced while paused — so the code forces one
with a `seekTo(pos + 1)` / `seekTo(pos)` round-trip. Its comment claimed "`seekTo(pos)` is
a no-op in Media3 when `pos == currentPosition`". That needed checking, because if the
round-trip were swallowed the effect would never reach a frame and the whole fix would be
invisible **even with the sink gate satisfied**.

Traced in the extracted 1.5.0 sources (`/tmp/m3src`, from the Gradle `-sources.jar`):

1. **`ExoPlayerImpl.seekTo` (line 904) has NO same-position early return.** It bumps
   `pendingOperationAcks`, moves the app-visible state to `STATE_BUFFERING` when it was
   `READY`, calls `internalPlayer.seekTo(...)`, and reports a position discontinuity. So
   the *comment's premise is wrong at this layer* — the short-circuit is one layer deeper.
2. **`ExoPlayerImplInternal.seekToInternal` (line ~1382) is where it actually happens:**
   ```java
   if (Util.usToMs(newPeriodPositionUs) == Util.usToMs(playbackInfo.positionUs)
       && (playbackInfo.playbackState == Player.STATE_BUFFERING
           || playbackInfo.playbackState == Player.STATE_READY)) {
     // Seek will be performed to the current position. Do nothing.
     periodPositionUs = playbackInfo.positionUs;
     return;
   }
   ```
   **The round-trip bypasses it by construction:** `pos + 1` fails the ms-equality test,
   and after the first seek the internal position is `pos + 1`, so the second seek fails it
   too. Both seeks therefore do real work. (The comment's *conclusion* is right, its
   *reason* is one layer off — worth sharpening, but it is a doc-only change and any edit
   right now would confound the pending device test, so it was left alone.)
3. **A real seek does flush and re-render.** `seekToPeriodPosition` (line 1423) →
   `stopRenderers()` → `mediaPeriod.seekToUs()` + `discardBuffer()` →
   `resetRendererPosition()` → `renderer.resetPosition()` for every enabled renderer →
   `MediaCodecVideoRenderer.onPositionReset` (codec flush), so one frame is re-decoded and
   rendered **through the current effect chain**.

**Conclusion: the chain is now unbroken end-to-end** — slider drag → long-lived effect
instance mutated → `setVideoEffects` → renderer message → `videoSink` (exists, thanks to
the constructor-time `setVideoEffects(emptyList())`) → `InputVideoSink` → per-frame
`getMatrix()` re-query → forced seek while paused → new frame through the updated matrix.

**New caveat found, not fixed (deliberate).** `SeekParameters` is left at the default
`CLOSEST_SYNC`, and `seekToInternal` feeds it to
`playingPeriodHolder.mediaPeriod.getAdjustedSeekPositionUs(...)`, which snaps to the
nearest sync sample. So after a slider drag while paused the displayed frame lands on a
**keyframe**, not exactly `pos`. That is *consistent* with the existing transport-scrub
behaviour (which already snaps), so it is not a regression — but it is the one plausible
"new symptom" a device test could surface ("the picture jumps when I move a slider"). The
fix would be confined to that single `if` block: `SeekParameters.EXACT` for the round-trip,
restoring any previously customised parameters afterwards. **Not applied** — the sink-gate
fix is still unverified on hardware and any further edit would confound that test.

**No code was changed this round.** Read-only verification.

## Round 6 — THE SINK-GATE "FIX" WAS ITSELF THE BUG: it killed playback

The user tested on device and reported a **new, worse** bug: not only did the colours still
not change, but **Play/Pause was completely dead and the video never played at all**. The
sink-gate fix from round 4 had to be reverted.

### Root cause — verified in the 1.5.0 sources

`setVideoEffects(emptyList())` at construction (and again before `prepare()`) made
`videoEffects != null` for the **first** `onEnabled`. That did create the GL sink — and
that is precisely what broke the player:

1. **`onEnabled` runs during `prepare()`**, and it only tells the new sink where to draw
   when a display surface already exists *at that instant* —
   `MediaCodecVideoRenderer:752`:
   ```java
   if (displaySurface != null && !outputResolution.equals(Size.UNKNOWN)) {
     videoSink.setOutputSurfaceInfo(displaySurface, outputResolution);
   }
   ```
2. **This screen has no display surface at that moment.** The foreground `PlayerView` is
   inflated inside the Compose `AndroidView` `factory`, so the surface attaches *after*
   the player is prepared. The file's own comment (the `onSizeChanged` post-mortem) already
   documented that the surface appears asynchronously.
3. **The surface never reaches the sink afterwards.**
   `setOutput()` — where the surface arrives — forwards it only when `videoSink == null`
   (that is where `videoFrameReleaseControl.setOutputSurface(displaySurface)` lives), and
   for the sink case it merely calls `videoSink.clearOutputSurfaceInfo()` when the surface
   is *removed*. Grepping every `setOutputSurfaceInfo` call site confirms the renderer has
   **exactly two**: line 752 (`onEnabled`) and line 963
   (`MSG_SET_VIDEO_OUTPUT_RESOLUTION`). Neither fires for a surface that appears late.
4. **Consequence:** the sink is created **blind**. The decoder renders into
   `videoSink.getInputSurface()`, the GL graph has no output surface to composite onto, so
   **no frame is ever produced**. `onFirstFrameRendered` never fires, the player sits in
   BUFFERING, `currentPositionMs` never advances, `onIsPlayingChanged` never reports true —
   and since the Play button is `exoPlayer.play()` guarded by `isPlaying`, pressing it
   looks like it does nothing at all. The colours still did not change because there were
   no frames left to colour.

**The lesson is not "the sink gate is a myth" — it is real. The lesson is that a one-shot
initialisation gate can have a *second* precondition, and satisfying the gate without
satisfying that precondition converts a silent no-op into a total failure.**
Here the precondition is `displaySurface != null` at the same instant. Because `onEnabled`
runs once per enable, a screen whose surface arrives late **cannot** satisfy the gate
safely — there is no moment at which both are true.

### Fix — revert to the healthy playback path

- Removed `setVideoEffects(emptyList())` from the player builder **and** from the
  media-item block. `videoEffects` now stays null, so the decoder renders straight to the
  display surface — the behaviour that plays. (This is also why the video played fine for
  months before round 4: the sink never existed, so the effects were silently dropped.)
- Removed the **entire** preview effect pipeline: the `GradeRgbMatrix` /
  `SharpnessEffect` / `VignetteOverlay` / `GrainEffect` instances, the `effectSignature`
  membership bits, the `setVideoEffects` call **and the paused-state seek round-trip**.
  No `setVideoEffects` call site remains in `EditorScreen.kt` (comments only).
- Kept the `onPlayerError` logging `DisposableEffect`. A `Player.Listener` that only calls
  `Log.e` cannot change playback behaviour — it is a pure observer, and it is the thing
  that would have named this failure. (The user suspected it; it is not implicated.)

### The colour path is now Compose — the user was right

Colour is applied as a `saveLayer` layer **on the foreground `AndroidView`**, using the
matrix that was already computed (`colorMatrix`, which already folds BCS + presets +
Lumetri + the upscaler CAS):

```kotlin
.drawWithCache {
    val layerPaint =
        if (ColorGradingMath.isIdentityMatrix(colorMatrix.values)) null
        else Paint().apply { colorFilter = ColorFilter.colorMatrix(colorMatrix) }
    onDrawWithContent {
        if (layerPaint == null) drawContent()
        else drawIntoCanvas { canvas ->
            canvas.saveLayer(Rect(0f, 0f, size.width, size.height), layerPaint)
            drawContent()
            canvas.restore()
        }
    }
}
```

Why this is safe **now** and was not in 2026-08-30:

- The old failure ("preview is black while audio plays") was diagnosed against a
  **SurfaceView**. The foreground player was switched to a **TextureView**
  (`R.layout.player_view_texture`, 2026-09-01, for the matting path). A TextureView's
  pixels *are* rasterised into the View hierarchy, so `saveLayer` captures them. The old
  diagnosis was correct for its surface type and does not apply to the current one.
- The old "it would double-apply the matrix" objection is gone: the Media3 effect chain it
  would have duplicated has been removed, so this is the **single** colour path.
- The old "dead on the API < 31 path" objection was **wrong** — only `RenderEffect` is
  API 31+; a `Paint.colorFilter` works from API 24 (`minSdk`). `saveLayer` is used
  precisely to avoid the `RenderEffect` gate.
- **Safety valve:** the layer is skipped entirely at an identity matrix, so a fresh project
  takes byte-for-byte the old code path and cannot regress to the black-screen bug. Only an
  actually-adjusted project enters the filtered path.
- No seek, no player state, no GL pipeline, no third-party lifetime gate. Dragging a slider
  only re-runs a Compose draw.

`Paint()` is allocated inside `drawWithCache` (once per matrix change), **not** inside
`onDrawWithContent` (once per frame) — a platform `Paint` per frame during a drag is pure
GC churn.

### Still export-only (unchanged, and now documented as such in-code)

`sharpness`, `vignette`, `grain`. They never reached the screen through the old code either
(the sink never existed), so removing them changes nothing the user could see — and a
colour matrix cannot express them anyway (a convolution and a spatial vignette are not
per-pixel colour transforms).

### Gate

`compileDebugKotlin` clean (one pre-existing `Icons.Filled.Notes` deprecation warning).
`testDebugUnitTest` = **1189 tests completed, 5 failed, 2 skipped** — byte-identical to the
baseline, all 5 the known Whisper/asset failures. No regressions.

### What is still unverified

The Compose layer is compile-verified only; whether `saveLayer` captures the TextureView on
the user's specific device needs their device test. The identity-matrix bypass means the
worst case is confined to the adjusted state rather than to the whole preview.

## Round 7 — the Compose `saveLayer` ITSELF broke the Play button; colour moved to the TextureView's own layer paint

The user tested on device and reported a **second, worse** regression: colour still did not
change **and** the Play/Pause button was dead, the video never played. Then they supplied the
decisive clue, in their own words:

> «قبل از اینکه اسلایدر را تکان بدهم، دکمه Play دقیق و درست کار میکند و ویدیو بدون مشکل
> پخش میشود. اما دقیقاً به محض اینکه یک اسلایدر (مثل Brightness) را تکان میدهم و مقدار آن
> از پیشفرض خارج میشود، دکمه Play کاملاً از کار میافتد!»
>
> ("Before I move a slider, Play works correctly and the video plays fine. But exactly as
> soon as I move a slider — e.g. Brightness — and its value leaves the default, the Play
> button completely stops working!")

That single sentence is a complete bisection: the player is healthy; the **colour code that
activates on the first non-default value** is the cause. Round 6 had removed every
player-level change, so the only thing that changes when the value leaves the default is the
**`saveLayer` branch in the `AndroidView`'s draw modifier** — its guard is
`isIdentityMatrix(colorMatrix.values)`, i.e. exactly "value == default". The identity bypass
that was added as a *safety valve* was in fact a perfect **switch** that the user could flip.

### Why the `saveLayer` was fatal

`drawWithCache { onDrawWithContent { drawIntoCanvas { canvas.saveLayer(...); drawContent(); } } }`
is a **re-entrant draw of the node's own content from inside that node's draw callback**. The
foreground `AndroidView` hosts a `TextureView` that is simultaneously compositing video, and
Compose's `drawContent()` on that chain re-enters the View drawing. The result is a draw loop
that never lets the frame finish — so the Surface/Texture pipeline stops presenting frames,
`onIsPlayingChanged` never fires, and the Play button (`exoPlayer.play()` guarded by
`isPlaying`) looks dead. **Any draw modifier whose output depends on Compose state
re-triggers that node's draw** — that is the shape that broke it.

### The fix — the user's proposal, verified from the platform source and adopted

Instead of `saveLayer` in Compose, set the filter **on the `TextureView` widget itself**:

```kotlin
textureView.setLayerType(View.LAYER_TYPE_HARDWARE, paintWithColorFilter)
```

Verified verbatim from the API 37 platform source at
`C:/android/sources/android-37.0/android/view/TextureView.java` (lines 355–380, 420–445):

```java
/**
 * The layer type of a TextureView is ignored since a TextureView is always
 * considered to act as a hardware layer. The optional paint supplied to this
 * method will however be taken into account when rendering the content of
 * this TextureView.
 */
@Override public void setLayerType(int layerType, @Nullable Paint paint) {
    setLayerPaint(paint);
}
@Override public void setLayerPaint(@Nullable Paint paint) {
    if (paint != mLayerPaint) { mLayerPaint = paint; invalidate(); }
}
@Override public int getLayerType() { return LAYER_TYPE_HARDWARE; }
```

and in `draw()`: `mLayer.setLayerPaint(mLayerPaint); recordingCanvas.drawTextureLayer(layer);`

So **no offscreen layer is created** (the layer type is ignored — a TextureView is always a
hardware layer) and the paint is applied **directly to the content**. This is a first-class,
documented platform mechanism, not a workaround: no `saveLayer`, no re-entrant
`drawContent()`, and **no path at all from the colour to the player, the Surface, or the
touch/event loop**. The user's diagnosis was exactly right.

Supporting facts, both verified rather than assumed:
- `androidx.media3.ui.PlayerView.getVideoSurfaceView()` is **public** (`PlayerView.java:1354`,
  `return surfaceView;`), and `PlayerView` builds the surface view in its **constructor** —
  `SURFACE_TYPE_TEXTURE_VIEW = 2` (line 288) → `surfaceView = new TextureView(context)`
  (lines 452–453). So the reference is valid immediately after inflation.
- Compose's `ColorMatrix` offset convention is **0..255** (same as `android.graphics`), so the
  paint needs **no rescaling** — checked precisely because it is the same value-shape trap as
  bug class #3.

### The six edits (`EditorScreen.kt`, the only file changed)

1. **Removed the `saveLayer`** from the foreground `AndroidView`'s modifier, restoring it to
   exactly `Modifier.fillMaxSize().graphicsLayer { … }`, with a comment forbidding anything on
   that chain from depending on the grade.
2. **Removed 6 now-unused imports** (`drawWithCache`, `geometry.Rect`, `graphics.ColorFilter`,
   `graphics.Paint`, `asComposeRenderEffect`, `drawscope.drawIntoCanvas`) — all remaining
   occurrences verified to be comments only — and **added `androidx.compose.runtime.SideEffect`**.
3. **Replaced the obsolete Layer-2 header comment** with the native-path design note
   (including the verbatim platform-source quote above).
4. **The factory now publishes the `PlayerView`** into a plain
   `remember { arrayOfNulls<PlayerView>(1) }` holder — deliberately **not** Compose state, so
   publishing a View reference triggers no recomposition, and the factory still runs exactly
   once (a second run would re-attach the Surface and drop the player).
5. **`previewColourPaint`** is built in `remember(colorMatrix)` as an
   `android.graphics.Paint` carrying
   `android.graphics.ColorMatrixColorFilter(colorMatrix.values)` — or `null` at an identity
   matrix. Rebuilt only when the grade actually changes, so `setLayerPaint` sees the *same
   instance* on every recomposition and no-ops (`if (paint != mLayerPaint)`), keeping the
   ~30 Hz position-poller recompositions free.
6. **A `SideEffect` after the `AndroidView`** applies it:

```kotlin
SideEffect {
    val textureView =
        foregroundPlayerView[0]?.getVideoSurfaceView()
            as? android.view.TextureView
    if (textureView != null) {
        textureView.setLayerType(
            android.view.View.LAYER_TYPE_HARDWARE,
            previewColourPaint
        )
    }
}
```

`as? TextureView` is a **guard, not a formality**: on a SurfaceView,
`setLayerType(LAYER_TYPE_HARDWARE, paint)` would allocate a *real* offscreen hardware layer
instead of just setting a paint — expensive and pointless. The `SideEffect` is also why the
`View` is published rather than the player: `SideEffect` runs after every successful
composition and needs a stable `View` reference.

### The transferable lesson (the sharpest one in this whole bug)

A "safety valve" that gates a risky code path on *the value being at its default* is not a
safety valve — **it is a switch the user will flip on their first action**, and it converts a
maybe-broken feature into a definitely-broken one at the exact moment they touch it. And when
a screen hosts a platform View that composites its own frames (TextureView/SurfaceView),
**never** put a Compose draw modifier on that node's chain: use the platform View's own paint,
which is applied on the render path rather than re-entering Compose's draw.

### Follow-up edit (same day): ordering-independent initial paint

The `AndroidView` factory and the `SideEffect` that follows it both run in Compose's *apply*
phase, but the relative order is an implementation detail (`InsertNodeFixup` vs change list).
After verifying from the Compose 1.7.6 runtime sources that `createNode` schedules a fixup
(rather than calling the factory eagerly), there was a residual risk: a saved project that
opens with a non-default grade might not have its initial paint applied if the factory ran
after the `SideEffect` on that first composition. To remove this dependency entirely, the
paint is now also applied **inside the factory** immediately after publishing the `PlayerView`:

```kotlin
(inflated.getVideoSurfaceView() as? android.view.TextureView)
    ?.setLayerType(
        android.view.View.LAYER_TYPE_HARDWARE,
        previewColourPaint,
    )
```

`TextureView.setLayerPaint` no-ops on an identical instance, so the second application (from
the `SideEffect`) costs one field comparison — zero risk of double-application.
