# 2026-09-17

## Coloured-canvas fade divergence — FIXED

Continues 2026-09-16's `canvasBackground` work; see that file for the plate
geometry. The one defect left over from that feature: the export folded
`1 - alpha` and `flashBlack` into a **single black wash**, so on a coloured
canvas the clip dimmed to black while the bars beside it stayed coloured. The
preview never did that — it composites the clip over the letterbox `Box` at its
own alpha, so it dims toward the *canvas* colour.

### The fix: split one wash into three

`TransitionGeometry` gained `fadeAlpha` / `flashBlackAlpha` / `needsFadeOverlay`
/ `needsBlackFlashOverlay` and **lost** `blackoutAlpha` / `needsBlackOverlay`.
The old pair conflated three sources into one pass:

- `fadeAlpha(pose) = 1 - frameAlpha(pose)` — the fade family, the fading motion
  presets and the `opacity` slider, all of which already multiply into
  `pose.alpha` via `ClipMotion.compose`.
- `flashBlackAlpha(pose) = pose.flashBlack` — an explicit black flash.
- `whiteoutAlpha` — unchanged.

`ClipMotionEffects.build` now takes `canvasBackground: CanvasBackground` and
emits up to **three** `ClipMotionWashOverlay` instances inside one
`OverlayEffect`, in the preview's paint order: fade (canvas colour) → black
flash → white flash. `ClipMotionWashOverlay`'s `whitePass: Boolean` became
`alphaOf: (TransitionPose) -> Float`, so the colour and the opacity source are
both chosen by the caller.

### Verified against the artifacts, not guessed

- **Overlay order.** `OverlayShaderProgram` generates
  `fragColor = getMixColor(fragColor, overlayN)` in list order, so the first
  overlay is bottom-most and each later one is drawn over the accumulated
  result. Read from the extracted `media3-effect` sources.
- **The preview's order.** `EditorScreen` layer 2.4 draws the black `Box` then
  the white `Box`; the `graphicsLayer { alpha }` below does the fade. The
  export's order now matches exactly.
- **The colour.** `CanvasLetterbox.fadeColorArgb(background)` is the single
  place that decides it — the plate and the fade are two consumers of one
  decision, so they cannot drift. A unit test asserts they agree on the same
  pixel. `Blur` and a zero-alpha swatch both map to black, matching the bars the
  export actually produces.

### The second defect the split fixed

The old `max(1 - alpha, flashBlack)` **under-darkened** any transition setting
both. `GLITCH` is the only built-in that does (`alpha = 1 - 0.08a` **and**
`flashBlack = 0.12a`): the preview leaves `0.92 * 0.88 = 0.8096` of the frame,
the old export left `1 - 0.12 = 0.88`. The behaviour change is confined to that
one transition; every other clip is byte-for-byte identical, because the fade
colour for `CanvasBackground.Black` *is* black.

### Also corrected

Stale "known gap" claims in `CanvasBackground.kt`, `CanvasBackgroundOverlay.kt`
and `VideoExportEngine.kt`'s call-site comment — the same class of documentation
rot the previous two rounds kept turning up. Rule reinforced: after shipping a
feature, grep for the words that described the *gap*, not just the code that
implemented it.

### Tests

`testDebugUnitTest` — **90 suites, 1127 tests, 0 failures, 0 errors, 0 skipped**
(was 1118). `CanvasLetterboxTest` 52 → 58 (six `fadeColorArgb` cases, including
the plate-agrees-with-the-wash assertion). `TransitionGeometryTest` and
`RenderGraphBuilderTest` updated for the renamed probes, plus new cases pinning
the independence of the two probes and the composed-opacity arithmetic.

### Still open

- `grain` — write-only in **both** renderers, so a feature the user never saw at
  all. Deferred: per-pixel noise, and every public route is unattractive.
- `CanvasBackground.Blur` — needs a second video sequence + `VideoCompositor`.
- **Device smoke test** — now five newly-wired GL paths (fade/`opacity`,

## A rotated clip on a FREE canvas lost every fade — FIXED

The second defect in the fade path, found by following the "known limitation"
note from 2026-09-16 rather than leaving it. **Supersedes the first "Still open"
list above.**

### The bug

`ClipMotionEffects.build` was handed the output frame size by the engine, and
skipped its full-frame washes when that size was unknown. There is exactly one
case where the engine cannot know it: **a FREE canvas with a single clip**, where
there is no `Presentation`, and step 1's `ScaleAndRotateTransformation` grows the
frame to the rotated bounding box *after* `ExportFrame.resolve` has already run.
`buildEditedMediaItem` detected that case (`frameIsKnown`) and passed `0`.

Consequence: **set a rotation on a single clip with the default canvas and the
fade silently became a cut** — along with every flash and the `opacity` slider.
A categorical failure, not a subtle one.

### The fix: observe the size, never guess it

`ClipMotionWashOverlay` now implements `configure(videoSize)` and sizes its
bitmap from the size Media3 reports there, rebuilding if it ever changes. That
is the same contract `VignetteOverlay` and `CanvasBackgroundOverlay` already
relied on, and it is verified: `OverlayShaderProgram.configure` calls
`overlay.configure(videoSize)` with the real dimensions, before any
`drawFrame`. So the size has gone from `ClipMotionEffects.build`'s signature
entirely — a value that is never passed cannot be dropped.

`outputHeightPx` stays, for one reason: it converts the pose's dp blur into a
pixel sigma, and `SeparableConvolution` exposes no `configure` hook with which
to observe the real height. That leaves a *bounded magnitude* approximation in
the same narrow case (the blur is scaled against the resolved height rather than
the rotated frame's), which is a different order of problem from an effect
disappearing — documented rather than papered over.

`frameIsKnown` survives as `hintWidthPx` / `hintHeightPx`, feeding only
`CanvasBackgroundOverlay`'s build-time "is there anything to paint" test. That
test is a pure optimisation: an unknown size means "keep the pass", which is the
safe direction, and the plate still decides per frame.

### Tests

Two new regression tests in `RenderGraphBuilderTest`:

- `a fading clip keeps its wash even when the frame size is unknown` — a
  `FADE_IN` clip with `rotation = 90` on a FREE canvas must still yield an
  `OverlayEffect` at `outputHeightPx = 0`.
- `a purely geometric clip emits no wash at all` — the counterpart, so the
  first assertion is not trivially true.

Constructing Media3 effect objects in a JVM unit test works because
`testOptions.unitTests.returnDefaultValues = true` is set, so
`BitmapOverlay`'s constructor (which calls `android.opengl.Matrix`) is a no-op
rather than a `Stub!` throw. Worth remembering: **Media3 effect *construction*
is unit-testable; only GL execution is not.**

`testDebugUnitTest` — **90 suites, 1129 tests, 0 failures, 0 errors, 0 skipped**.

### Still open

- `grain` — write-only in **both** renderers. A real feature, deliberately
  deferred: per-pixel noise, and every public route is unattractive.
- `CanvasBackground.Blur` — needs a second video sequence + `VideoCompositor`.
- **Device smoke test** — six newly-wired GL paths now (fade/`opacity`,
  sharpness, vignette, canvas background, the fade colour, and the observed wash
  size). Unit tests verify the geometry and the arithmetic; they cannot verify
  that a shader composites the way we expect.
- The dp-blur sigma in the FREE-canvas + rotation case (see above).
- `AiJobEngineTest.cancelTransitionsToCancelledNotError` — known flake.

## `grain` implemented — the last write-only field

**Supersedes the "Still open" list above.**

### What it was

`ColorGrading.grain` was write-only in **both** renderers: `ColorGradingPanel`
wrote it, Room persisted it, nothing read it back. That made it unique in this
whole series — every other field closed had a *preview behaviour to match*, so
the appearance was already decided and the job was to reproduce it. Grain had
never been rendered anywhere, so its look had to be **decided**, which is a
different and much more open-ended problem.

### The route, and what was rejected

| Route | Why not |
|---|---|
| Downscaled bitmap plate (the `VignettePlate` trick) | Grain is *high-frequency*; GL's linear upscale turns it into soft blobs. The trick only works for a gradient. |
| Per-frame full-resolution `BitmapOverlay` upload | ~8 MB/frame at 1080p → ~250 MB/s at 30fps. Not affordable on a mobile GPU. |
| One static noise texture | Free per frame, but reads as dirt on the lens — real grain **moves**. |
| `ByteBufferGlEffect` | The same custom GL surface as a shader, *plus* a per-frame CPU pass over every pixel. |

Chosen: a **custom fragment shader** — the project's first hand-written one.

### Files

- `model/GrainSignal.kt` (**new**) — the pure, unit-tested specification.
- `export/GrainEffect.kt` (**new**) — the `GlEffect` + `BaseGlShaderProgram`.
- `app/src/main/assets/shaders/fragment_shader_grain_es2.glsl` (**new**).
- `export/VideoExportEngine.kt` — new pass **4.7**, after the vignette and
  before the `Presentation` (so it lands on the *source* frame, the frame the
  preview's effect chain sees).
- `ui/screens/editor/EditorScreen.kt` — `grainEffect` remembered once,
  `useGrain`, `effectSignature` **bit 8**, `grain` written per recomposition.

### The model (there was nothing to match)

- **Amplitude** = `grain * MAX_AMPLITUDE` (0.25), linear in the slider.
- **Response** = `4·l·(1-l)` — zero in pure black and pure white, peak at
  mid-grey. Deliberately **not** mean-normalised. This is the single biggest
  difference between convincing grain and obvious fake grain: flat noise across
  the whole range reads as TV static and wrecks clean blacks.
- **Monochrome** — one delta on all three channels. A per-channel hash would
  read as chroma noise and shift the picture's hue.
- **Seed from the presentation timestamp** (`% 1 s`), not a frame counter, so
  the preview and the export agree. A counter diverges whenever their frame
  rates differ.

### Verified against the artifacts

- Every API used was `javap`'d on the extracted 1.5.0 jars first.
- `GrainShaderProgram` was then compared **line by line** with Media3's own
  `AlphaScaleShaderProgram`: same super-constructor args, same
  `aFramePosition` buffer attribute, same two identity matrices, same
  `configure` pass-through, same `use → sampler → uniforms →
  bindAttributesAndUniforms → glDrawArrays(GL_TRIANGLE_STRIP, 0, 4)` order,
  same exception translation.
- The `vTexSamplingCoord` varying matches
  `vertex_shader_transformation_es2.glsl` **exactly** — read from the merged
  assets, not assumed. A mismatch would be a link failure or a garbage read.
- `BaseGlShaderProgram.release()` deletes **only** the texture pool; the
  convention in every concrete Media3 program is
  `super.release(); glProgram.delete()`. So the added `release()` is not a
  double-free — and it is *more* correct than the template, because
  `AlphaScaleShaderProgram` is the one Media3 program that never deletes its
  program.
- The asset is in the APK: `assets/shaders/fragment_shader_grain_es2.glsl`,
  4039 bytes, confirmed by reading the zip.

### Two traps worth remembering

- **`setFloatsUniformIfPresent` is a silent no-op for an undeclared name.** A
  one-character uniform typo would produce no error and no effect, ever. Guarded
  with an explicit `getUniformLocation(name) < 0` check in the constructor, so a
  typo fails loudly at pipeline-build time instead.
- **`mergeDebugAssets` only runs on a real `assemble`, not on
  `testDebugUnitTest`.** A unit-test-only loop therefore cannot catch a missing
  or misplaced shader file — which is the one failure mode of a new shader that
  tests structurally cannot see. Ran `assembleDebug` specifically to prove it.

### Documentation sweep

Grepped for the words that described the *gap* — the standing hazard, and it
caught four more stale sites: `VignettePlate.kt` ("grain is still
unimplemented"), `VignetteOverlay.kt` (the `frameIsKnown` claim about the fade
washes, now that they observe their size too), `VideoExportEngine.kt` ×2
("unlike the fade washes, whose size the engine has to guess" and "the black
fade wash", which is now the canvas-coloured wash), and an "All four" that
should have been "All three" in `ColorGradingMath.kt`.

### Tests

`testDebugUnitTest` — **91 suites, 1161 tests, 0 failures, 0 errors, 0 skipped**
(was 90 suites / 1129 tests). The +32 is `GrainSignalTest`, the new suite.
`assembleDebug` also green.

### Still open

- `CanvasBackground.Blur` — needs a second video sequence + `VideoCompositor`.
- The dp-blur sigma in the FREE-canvas + rotation case.
- **Device smoke test** — now **seven** newly-wired GL paths: fade/`opacity`,
  sharpness, vignette, canvas background, the fade colour, the observed wash
  size, and the hand-written grain shader. Unit tests verify the geometry, the
  arithmetic and the effect-chain shape; they cannot verify that a shader

## `AiJobEngine` cancellation race — FIXED (and the "flaky test" explained)

### The test was right

`AiJobEngineTest.cancelTransitionsToCancelledNotError` had been carried for two
sessions as a "known load-sensitive flake". It was not a flaky test. It was
intermittently **correct**: it asserts `cancel()` returns true while the worker
is running, and there was a real window in which the worker *was* running but
`cancel()` could not find it.

### The race

```kotlin
val coroutineJob = scope.launch { ... }   // default start mode dispatches NOW
activeJobs[toolId] = coroutineJob          // registered AFTER launch returns
```

`scope.launch` with the default start mode dispatches immediately, so the block
could already be executing on a pool thread before `launch` returned — i.e.
before the registration line ran. `cancel()` does
`activeJobs.remove(toolId) ?: return false`, so a cancel landing in that window
returned `false` and was **silently dropped** while the job ran to completion.
The same class of silent failure as everything else in this series.

### The fix

`CoroutineStart.LAZY`, then register, then publish `PREPARING`, then `start()`:

- The worker cannot begin before it is registered, so "the block has started"
  now implies "cancel() will find it".
- Publishing `PREPARING` **after** registration (it used to be before) closes a
  second window: an observer reacting to the flow can no longer see a job that
  is not yet cancellable. Safe because the `Progress` sink guards its updates on
  `current.id != jobId` and is only ever called from inside the block, which
  cannot run before `start()`.
- `cancel()`'s KDoc now states the guarantee instead of leaving it implicit.

### The fix had a bug of its own — caught before shipping

Cancelling a LAZY job that has never run means the body never executes, so
nothing ever completes `deferred` and `deferred.await()` would suspend
**forever**. A hang is worse than the dropped cancel it replaced. Added
`coroutineJob.invokeOnCompletion { ... deferred.cancel(...) }` as a backstop,
which also covers the engine's scope being cancelled (that hung too).

### The regression test, measured honestly

`aStartedJobIsAlwaysCancellable` — 200 iterations; the block calls `cancel()` as
its first action, the earliest moment a cancel can arrive.

**It does not reproduce the old bug.** I restored the buggy ordering and ran it:
all 200 iterations passed on an idle JVM. The window is only a few instructions
wide and needs *load* to widen. So it is a **guard on the invariant, not a
reproduction** — it would fire if the window were ever widened again (a
`yield()`, an `await()`, or a `withContext` between the launch and the
registration would do it). The test's own KDoc says exactly this, so nobody
later assumes it caught the bug.

Also hardened the original test: `started.await(1, SECONDS)` became 5 s (a
second, unrelated flake axis under full-suite load), and its final
`deferredOutcome.await()` is now bounded so a cancellation regression fails
instead of hanging until Gradle's timeout.

### Lesson

A test carried as "flaky" for two sessions was reporting a real defect. **When a
test flakes, suspect the code before the test.** And after writing a regression
test, try to make it fail; if it will not, say so *in the test*.

### Tests

`testDebugUnitTest` — **91 suites, 1162 tests, 0 failures, 0 errors, 0 skipped**
(was 1161).

## The dp-blur sigma residual — FIXED (it was never actually an approximation)

### What was documented

`ClipMotionEffects.build`'s `outputHeightPx` converts a pose's `blurDp` into a
pixel sigma as `blurDp * (outputHeightPx / 430)`. It was carried as a *bounded
magnitude approximation* in one case: a FREE canvas holding a single rotated
clip, where `ExportFrame.resolve` runs before step 1's
`ScaleAndRotateTransformation` grows the frame to the rotated bounding box — so
the blur was scaled against the resolved height rather than the frame height.

### Why "approximation" was the wrong word

The value is knowable, and the code already knew it:

- `ExportFrame.needsPresentation` is
  `(canvasPreset.exportWidth > 0 && canvasPreset.exportHeight > 0) || multiClip`.
  So "no `Presentation`" means a FREE canvas holding **one** clip — and then
  `frameReference == segment`, i.e. the resolved size *is* this segment's size.
- The call site's own comment said it: *"With no Presentation it is the source's
  own size, which is what the caller resolved — except when step 1's rotation
  grew the frame."*
- **The frame entering step 1 is the resolved size**, so the post-rotation frame
  is simply `rotatedBounds(resolvedW, resolvedH, rotation)`.
- `CanvasLetterbox.rotatedBounds` already existed, was already unit-tested via
  `videoRect` / `needsPlate`, and is the *same* function the canvas plate uses —
  so reusing it keeps the two passes agreeing on what "the frame" is.
- `frameIsKnown` already encoded the exact predicate. It just wasn't fed to the
  blur.

### The fix

New pure helper `blurReferenceHeightPx(resolvedWidthPx, resolvedHeightPx,
rotationDegrees, frameIsPinned)` in `ClipMotionEffects.kt`, placed next to
`ClipMotionBlurEffect` — its only consumer — and in the same package as both the
caller (`VideoExportEngine`) and the tests (`RenderGraphBuilderTest`), so
**neither side needed an import**. `VideoExportEngine` passes
`frameIsPinned = frameIsKnown`.

### A discovery along the way

`RenderSegment.rotationDegrees` is an **`Int`**, and its KDoc restricts it to
`0 / 90 / 180 / 270`. So the clip's frame rotation is always a quarter-turn and
the bounding box is **exact** — no partial-angle rounding can creep in. (The
`Float` in `rotatedBounds` exists for *pose* rotation, which is genuinely
arbitrary: the transition presets rotate by a few degrees.) The helper therefore
takes an `Int`, and the non-finite-rotation test written first was impossible —
replaced with 180° and 270° cases, which are the ones that can actually occur.

That was found by a compile error: I had assumed `Float` and the compiler
rejected it. Reading `RenderSegment` then *simplified* the fix rather than
complicating it.

### Tests

Six new in `RenderGraphBuilderTest` (42 → 48): pinned, unrotated, rotated, 180°,
270°, and degenerate. `testDebugUnitTest` — **91 suites, 1168 tests, 0 failures,
0 errors, 0 skipped**.

### Lesson

**A documented approximation may not be an approximation — check whether the
value is knowable before accepting it as a limitation.** This one had been
carried as an honest residual for two sessions and turned out to be exactly
computable from values already in scope.

Corollary, and the more reusable half: **before writing new geometry, grep for
the geometry you already have.** The rotated bounding box was already there,
already tested, and already relied on by the neighbouring pass.





## Matting parity: the docs had it backwards (2026-09-17, evening)

The engine KDoc said "Background Remove (Matting) is preview-only — the export
pipeline just doesn't consume them yet". Exactly backwards:

- **Export composites for real** — as a CPU pre-render, not an effect:
  `AiExportHooks.prepareSourceUri` (called for EVERY segment on the live export
  path, engine ~line 273) → `compositeMatting` → `VideoFramePipeline.transcode`,
  blending `mix(bg, fg, a)` per frame from the sidecar alpha PNGs, audio copied
  sample-for-sample. Modes: ORIGINAL pass-through, BLUR (1/8 downscale +
  bilinear upscale), COLOR, IMAGE (cover-crop), VIDEO (`BgVideoSampler`).
  TRANSPARENT throws a user-facing `AiExportException`. `threshold` is read as a
  soft knee (`[0.6t, 0.6t+0.4]`, smoothstep) in `compositeFrame`.
- **Preview does not composite at all** — only the "BG Remove ready" chip.
  Compose can't sample TextureView/SurfaceView pixels; the sibling-Box
  RenderEffect route was proven inert (2026-09-16, Layer 2.5 note) and no
  "Layer 2.6" matting overlay exists anymore.
- `PersonMatteEffect` is a dead stub — never instantiated anywhere; its KDoc had
  BOTH directions wrong (export "preview-only", preview "fully working").
- `EditorViewModel.previewMattingReady` has NO collector — the chip reads
  `uiState.aiTools["matting"]` status directly.
- `MattingSettings.featherPx` is persisted but never read — the real feather is
  a hard-coded `2f` in `MediaPipeMattingEngine` (`applyFeatherAlpha`), baked
  into the sidecar PNGs at analysis time. A write-only field hiding in plain
  sight (its stored value coincidentally equals the hard-coded constant).

Doc fixes: VideoExportEngine (bullet + table row + Background-Blur
disambiguation), PersonMatteEffect (KDoc + inline), RenderSegment `@param
matting`, EditorViewModel `previewMattingReady`, EditorScreen x2. The
"BG (blur)" table row (canvas letterbox blur) is a DIFFERENT feature and stays
preview-only — now explicitly disambiguated from matting's BLUR background
mode, which IS exported.

Lesson, same family as the grain sweep but bigger: grep for the gap vocabulary
(`preview-only`, `not implemented`, `has no consumer`) and read the *call graph*
behind each hit — features get implemented through routes the old docs never
mentioned. The skill's diagnostic-table row "Export-only — check the preview is
not silently inert" was the right prediction all along.

## Preview blur background was sharp (2026-09-17, evening)

`CanvasBackground.Blur`'s preview layer (EditorScreen Layer 1) built
`PlayerView(ctx)` — default `surface_type="surface_view"` — and applied
`Modifier.blur(36.dp)`. SurfaceView content is composited outside the View
raster, so the blur had nothing to act on: the "blurred" background was a sharp
ZOOM-cropped copy on every device. Third occurrence of the same trap (colour
tint, preview grade, now this). Fix: inflate `R.layout.player_view_texture`
(the same layout Layer 2 uses). Residuals: `Modifier.blur` is a no-op below
API 31 regardless, so API 24-30 still shows a sharp background; and the export
renders this mode's bars black (the documented preview-only gap). Unit tests
can't catch either side (no GL, no device).

## Removed dead `previewMattingReady` flow (2026-09-17, night)

`EditorViewModel.previewMattingReady` was a `StateFlow<Boolean>` with **zero**
collectors — no Compose `.collectAsState()`, no test reference, no other
ViewModel read. The "BG Remove ready" chip in `EditorScreen` reads
`uiState.aiTools["matting"]` status directly, which is cheaper and already
covers the signal. Removed the entire property to prevent future readers from
assuming it drives the UI. The KDoc had already documented it as dead; deleting
it closes the ambiguity.
