# 2026-09-28 — Motion Tracking design (docs/MOTION_TRACKING_IMPLEMENTATION.md)

Wrote a full Phase 1–5 implementation guide for an offline 2D motion-tracking / overlay-attach
feature. No code changed — design document only. Key findings from reading the tree:

- **~60% of the feature already exists** under different names. Do NOT build a second tracker.
  - `ai/media/VideoFramePipeline.kt` — `transcode` + `FrameOp` = hardware decode, exact PTS,
    rotation-corrected, memory-bounded. **This is the correct frame feed**, NOT `cv::VideoCapture`
    and NOT per-sample `MediaMetadataRetriever` (which snaps to keyframes via `OPTION_CLOSEST_SYNC`).
  - `ai/engines/SaliencyTrackerEngine.kt` — already a 3-tier semantic tracker (Pose → BlazeFace →
    Sobel saliency) with multi-person cost-based target locking, loss recovery
    (`LOSS_RECOVERY_SAMPLES = 8`), and a **1-Euro filter**.
  - `model/AiToolSettings.kt#CropKeyframe` — normalized trajectory model, persisted per clip.
  - `export/AiExportHooks.kt#reframe` — the per-frame consumer (`interpolateKeys` → `cropWindowFor`
    → `FrameOp`), the exact template for baking a tracked overlay.
- **Reframe: generalize the existing pipeline from a crop *centre* to a tracked *box + confidence*,
  then add a new consumer that attaches an overlay instead of cropping.** Three new files, rest is
  extension.

Design decisions recorded (with rationale in the doc):

1. **Two-tier hybrid tracker.** Tier A = existing MediaPipe (semantic, re-acquirable, identity-
   correct) every ~3rd frame at 360p. Tier B = `TrackerCSRT` per frame on an ROI crop grown 1.6×
   (~3–6 ms, cost scales with search window not frame). Pure single-tracker approaches each fail:
   CSRT alone cannot re-acquire after occlusion or hold identity; detectors alone have no landmark
   for a fingertip.
2. **Reject EMA and 1-D Kalman.** The existing 1-Euro filter is adaptively better (cutoff rises with
   speed → smooth at rest, responsive when moving). Extract it from the `@Singleton` engine to
   `model/OneEuroFilter.kt` so it becomes JVM-testable per the "pure top-level function" rule.
3. **Widen `CropKeyframe`; do not fork a `MotionTrackKeyframe`.** Additive nullable
   `width?`/`height?` + `confidence`/`isFound` with defaults that reproduce Auto Frame exactly.
   `width`/`height` MUST be nullable — a non-null default would silently invite a future consumer
   to read extent and change Auto Frame behaviour. Two parallel keyframe lists would mean two
   `RenderSegment` fields, two JSON paths, two Room columns → the project's worst bug class
   (preview/export divergence).
4. **`isFound` is the highest-value field.** Enables hold → coast-with-alpha-decay → fade back in on
   re-acquire. Forward-filling without it produces a visible snap that reads as broken.
5. **Smooth at full rate, then decimate to keyframes** — matching the order
   `SaliencyTrackerEngine.process` already uses. Smoothing an already-decimated list filters an
   aliased signal.
6. **Re-anchor discontinuities cannot be smoothed** (a 0.3→0.7 jump spread over frames = a swoop).
   Fix belongs in the *consumer* as an alpha ramp, not in the filter.
7. **Export via `FrameOp`, not FFmpeg and not a Media3 `TextureOverlay`.** Decisive reason: the
   overlay must be rasterized by the same Persian-aware renderer the preview uses
   (`CaptionRenderer`/`SubtitleBurnIn`), guaranteeing parity. Rasterize the stamp ONCE, then blit.
   Must return `src` modified in place — a new bitmap per frame OOMs.
8. **Export ordering: matting → reframe → tracked overlay.** Attaching before a reframe means the
   reframe crops the sticker away.
9. **Preview cannot show a tracked blur/mosaic** — the video composites via `TextureView` outside
   the View raster (`MEMORY.md` bug class 2). Consistent with `sharpness`/`vignette`/`grain` being
   export-only. Tracked text/sticker is fine as a sibling Compose layer. Never put a Compose draw
   modifier on the `AndroidView` chain (round-6 `saveLayer` killed the Play button).
10. **Confidence is derived, not measured** — OpenCV's `Tracker` API exposes no score for KCF or
    CSRT (only Nano does). Use NCC template residual + motion prior.

Also flagged: `interpolateKeys` return type changes `Pair<Float,Float>` → `CropKeyframe` (one call
site, deliberate compile-checked break). Keyframe density must go 5 fps → 30 fps for overlay
binding (5 fps visibly steps). OpenCV is NOT currently a dependency; NDK+CMake path exists
(`whisper-jni.cpp`, `abiFilters = arm64-v8a` only). Two claims flagged as unverified:
`Class.forName("org.opencv.tracking.TrackerCSRT")` (the Maven artifact's `tracking` module contents)
and the rotated-source coordinate identity.

### Compile traps hit (all mechanical, worth remembering)

1. **Kotlin forbids a nested `typealias`.** Extracting the 1-Euro filter left
   `internal typealias OneEuroFilter = ...` *inside* the class → `Nested and local type aliases are
   not supported`. Fix: declare it at **file scope** (private top-level). The call site
   `OneEuroFilter(smoothing).smooth(trace)` then compiles unchanged. A typealias is the right move
   here — a rename would have touched Auto Frame's hot path for no benefit.
2. **`android.graphics.Rect` vs Compose `Rect`.** `RoiSelectorOverlay` is Compose and passes
   `androidx.compose.ui.geometry.Rect`; the tracker/`FrameOp` side speaks `android.graphics.Rect`.
   `MotionTrackingGeometry` must therefore expose **the Compose type** for frame rects (`videoFrameComposeRect`,
   `toNormalized`/`toContainer`/`rectToContainer`/`rectToNormalized` all take Compose `Rect`), and
   keep `android.graphics.Rect` only for the source-pixel conversions (`toSourceRect`,
   `toNormalizedRect`, `videoFrameRect`). Mixing property and method syntax (`frame.width` vs
   `frame.width()`) produces a dozen confusing errors — pick one type per direction.
   Also: `Rect.Zero` **does not exist** on `android.graphics.Rect` (use `Rect(0,0,0,0)`), and its
   ctor takes **Ints**, so a letterbox computation must `roundToInt()`.
3. **No `org.opencv.*` import may exist in the source set.** The dependency is gated behind
   `-PwithOpenCv=true`, so an unconditional import breaks the default build. `OpenCvRoiTracker` is
   therefore **fully reflective**: `Mat`/`Utils`/`CvRect`/`CvType` are `Class.forName`d and held as
   `Any`, with `Method`/`Field` handles cached in the ctor. This also makes a missing `tracking`
   module (or a broken native load, which surfaces as `UnsatisfiedLinkError` — an `Error`, not an
   `Exception`) degrade to the NCC backend instead of crashing.
4. **`.weight(1f)` needs `RowScope`.** A helper `@Composable fun Chip(...)` that calls
   `Modifier.weight` must be declared as `RowScope.Chip` — otherwise `Unresolved reference 'weight'`.
5. **`VideoClip` has `width`/`height`, not `displayWidthPx`.** They are the rotation-corrected
   display dimensions `sourceAspect` is already computed from; use them for the frame rect.

### `unitTests.isReturnDefaultValues = true` — the trap that cost a round

`build.gradle.kts:135` sets this, which makes **every `android.*` method return `0`/`0f`** on the
JVM. A `RectF` built in a test therefore reads back as `(0,0,0,0)`, so 11 new geometry tests
"passed or failed for the wrong reason" — all failing with `expected:<400> but was:<0>`.

Fix, and the rule going forward: pure rectangle geometry is expressed in **plain floats**.
`MotionTrackingGeometry` now has a `data class NormBox(left, top, right, bottom)` with
`width`/`height`/`centerX`/`centerY` derived properties, plus a `videoFrameBox(w,h,dw,dh)` that
returns one. Every `RectF`/`Rect`/`IntSize` entry point is a one-line delegation to the float
version. Compose `IntSize` and `Rect` are **also** inert here (verified), so don't reach for them
as a "safe" alternative.

### A real bug the tests caught

`lerpNullable(a = null, b = 0.3f)` originally returned `b`, i.e. it **fabricated an extent** for a
trajectory that never had one — an Auto Frame keyframe being lerped against a Motion Track one
would suddenly report a tracked box, defeating the whole point of widening `CropKeyframe`
additively instead of forking it. Now `null` wins when either side lacks an extent. The test
`interpolateKeyframe tolerates an Auto Frame entry with no extent` pins it.

### The load-bearing discovery: Media3 1.5.0 already has the hard part

Extracted the `-sources.jar` from the Gradle cache. `SpeedChangeEffect(SpeedProvider)` (video,
updates frame timestamps, drops no frames) and `SpeedChangingAudioProcessor(SpeedProvider)` (audio,
delegates to `SonicAudioProcessor` → pitch-preserving) both exist, plus
`SpeedProviderUtil.getDurationAfterSpeedProviderApplied` (integrates `Σ Δt/v`). **So "implement
Sonic time-stretch" reduced to writing a curve-backed `SpeedProvider`.** No new audio subsystem.

### `SpeedProvider` is piecewise-CONSTANT — this dictates the whole design

`SpeedChangeShaderProgram.queueInputFrame` walks boundaries with
`output += (inputTime - lastSpeedChangeInputTime) / speedProvider.getSpeed(inputTime)` and
`while (nextSpeedChangeInputTimeUs <= presentationTimeUs)`. Therefore:

1. `getNextSpeedChangeTimeUs` must return a value **strictly greater** than its argument (returning
   `t` loops forever). Verified: a negative query must answer `0`, not `TIME_UNSET` — `TIME_UNSET`
   would bake slice-0's rate over the entire clip.
2. The interpolator must **pre-sample the ramp onto a source grid** (`SLICES_PER_INTERVAL = 32`,
   clamped `MIN_STEPS 64`..`MAX_STEPS 2048`) and sample each slice at its **start**, reproducing
   Media3's staircase exactly, so the shader's PTS accumulation and the duration prediction agree.
   A test reimplements Media3's walk and asserts agreement with `totalOutputDurationUs`.
3. The provider is sampled on the **INPUT (source)** timeline → `SpeedPoint.normalizedTime` is
   **source-relative**, not output-relative.

Also: `∫dt/v` is a **harmonic** mean. Half at 0.5× + half at 2× is 25% *longer*, not equal length.

### Design decisions taken (user-facing, recorded so they aren't re-derived)

1. **Curve range is its own 0.1×–10×; `PlaybackSpeedRange` (0.25×–4×) is untouched.** The graph
   axis draws a **symmetric 0.125×–8×** window (`2⁻³..2³`, log2) so 1× sits at exactly 50% height —
   the first draft used `0.25..8`, which put 1× at 60% and *looked* biased toward slow motion. Caught
   by the y-axis test; it was a real design flaw, not a bad test.
2. **Preview plays the ramp's effective AVERAGE rate** (`rampedPreviewSpeed`), disclosed in the
   panel. `ExoPlayer.setPlaybackParameters` is a single constant rate; a real ramped preview would
   need a `SpeedProvider` wired into the preview player. The **export applies the full curve.**
3. **Do NOT remap PTS in `VideoFramePipeline`.** AI pre-renders (matting/autoframe/motion track) run
   through it *before* the Transformer, which then applies the curve → ordering is
   spatial-then-temporal, no double-apply. Adding a PTS remap there would double the ramp.
4. **Do NOT touch `EditorTimeline`** — it was never speed-aware (a 2× clip already draws at source
   width). Making it ramp-aware would move auto-layout and hit-testing for no gain here.

### Two real pre-existing bugs found and fixed in passing

1. **`motionTrack` was silently dropped from 3 of the 4 persistence sites** in `EditorViewModel`
   (only one inline `ClipAiTools(...)` literal carried it). Fixed by centralising into a file-scope

2. **`splitClip` replayed the whole ramp in both halves.** Fixed with

Also fixed `RoomProjectRepository.toVideoClip` dropping `motionTrack` (fell back to `Identity`).

### The DSP design, and what each gate actually rejected

`BeatDetector` runs a 512-point Hann-windowed FFT, 128-sample hop (75% overlap, ~5.8 ms/frame at
22.05 kHz), positive frame-to-frame magnitude difference summed per band (kick 20–150 Hz, snare
150–2000 Hz, kick weighted 1.35×). Then `pickPeaks` applies four gates in order — an absolute floor
(`globalPeak * 0.02`), the `mean + k·σ` adaptive threshold (`k` = 2.0/1.45/1.0 for
آرام/معمولی/سریع), a duty-cycle gate (`ACTIVITY_DUTY_LIMIT = 0.55`), and an attack-shape gate
(`MAX_ATTACK_RATIO = 1.6`).

**A sustained tone was detected as a beat train, and only measurement fixed it.** Findings, in the
order they were established — each one killed a plausible-looking theory:

1. **Frame 0 is spurious.** `prevMag = 0` makes its "flux" the absolute magnitude at t=0, which
   also corrupts the adaptive statistic for ~800 ms. Seed the baseline and report zero novelty.
2. **`mean + k·σ` alone fails** — 81 of 513 frames of a 220 Hz tone cleared it. The leakage
   artifact is quasi-periodic with a low duty cycle *and* inflates σ, so it raises its own
   threshold.
3. **Median/MAD is worse** (131 frames, not 81).
4. **Spectral whitening** (per-bin causal baseline, decay 0.90) improved contrast 5–6× — kicks
   reach 17–21× while tones sit at 2.4–3.6× — but did not fully solve it.
5. **Duty cycle separated most cases** (110/220/440/1000 Hz tones 0.9986 vs 120 BPM kicks 0.1498)
   but **40 Hz measured 0.5528**, sitting exactly on the 0.55 limit: 40 Hz is 3 Hz from bin 0's
   centre (bin spacing is 43.07 Hz), so its leakage modulates *slowly* (~645 ms) and mimics a
   ~93 BPM kick train.
6. **Raising the kick-band lower edge made it worse** (110 Hz then produced 8 markers) — removing
   bins deleted the continuous energy and left only the sparse modulation. Reverted
   `KICK_BAND_LOW_HZ` to `20f`.
7. **Attack-shape asymmetry** (`isPercussiveAttack`: a strike rises fast / decays slow, ratio < 1)
   rejected 7 of 8 tones, but 1900 Hz still passed at ratio 1.01, and the ratio varies 1.01–2.10
   with a wide spread per tone — **no single constant works**, so this alone cannot be the gate.

**The decisive test is stationarity**, not any of the above: `spectralActivityRatio` =
`mean|ΔM| / mean energy` over the whole spectrum and buffer. Measured **0.0000–0.0170 for steady
tones, 0.2904/0.2901 for 120/150 BPM kicks, 0.1348 for kicks over a sustained pad**. Threshold
`MIN_SPECTRAL_ACTIVITY = 0.05` gives ~3× margin on both sides and is checked *once per buffer*
before peak picking, which is why it costs nothing per frame. **Do not remove it and do not lower
it** — every steady-tone false positive comes back.

### Two arithmetic traps worth remembering

- **Refractory truncation.** `(200ms * 22050 / 1000 / 128).toInt()` = 34 frames = **197.37 ms**,
  violating a 200 ms guarantee. Use `ceil` → 35 frames → 203.17 ms.
- **`MIN_MARKERS_FOR_BPM = 6`.** A 2 s train at 500 ms gives only 4 onsets, so `bpm` is correctly
  `null` — that was a test that overreached, not a code bug. Short tracks legitimately report
  markers but decline a tempo.

### UI decisions

- **Beat ticks are mirrored constants, not shared ones.** `BeatMarkerYellow` lives in `BeatPanel.kt`
  and `TimelineBeatYellow` in `EditorTimeline.kt` (same value `0xFFFFD54A`), deliberately, so the
  timeline module does not depend on the panel module. Same for `BEAT_SNAP_MS` /
  `TIMELINE_BEAT_SNAP_MS`, and `TOOL_ID_BEATS` / `BEAT_TOOL_ID`. **If you change one, change both.**
- **`snapToBeatMarkers` delegates to `BeatDetector.nearestMarker`** rather than scanning locally.
  The first draft was a linear scan; that would have been a *second* implementation of "nearest
  marker" alongside the ViewModel's snap path, and the already-tested binary search (with a
  brute-force cross-check test) is the authority. Costs one throwaway `AudioBeatData` allocation per
  drag callback — irrelevant next to the correctness win.
- **Beat snap is 18 ms; boundary snap stays 80 ms.** Intentional and user-visible: snapping to a
  beat is only worth anything if it is precise, and 40 ms off the kick is the defect the feature
  exists to remove. Beats are checked *first*, so a beat nearly on a boundary wins.
- **Ticks are drawn on the video lane too.** A video clip has no `beatData` of its own — the music
  is usually a different lane — so `VideoBeatMarkerStrip` reads the flattened project list and does
  a strict-interior range filter (a tick exactly on a block boundary would be drawn twice and read
  as a thicker line, misrepresenting where the beat is).
- **`beatMarkers` is threaded through as a parameter, defaulting to `emptyList()`**, so every
  pre-existing caller, preview and test keeps compiling and the beat snap is a no-op for projects
  that never ran Detect.

### `autoSplitOnBeats` — three things that had to be right

`splitClip(clipId, splitTimelineMs)` takes a **global timeline** position and **pushes history
itself**, so: cuts are applied **last-to-first** (`splitClip` renumbers following clips, so working
backwards keeps every position valid); history is pushed **once** before the batch (a montage cut
is one undo step, not one per beat); and because `splitClip` returns `Unit`, the count of applied
splits is derived from the **clip-count delta** rather than assumed.

### ⚠️ New trap found — Compose `weight(1f)` + fixed-size child
`RowScope.weight(1f)` (default `fill = true`) gives a child **exactly** its share; it cannot grow
past it. `iOSToolbarItem` had a **fixed 36dp icon tile**, so in CLIP context on a 360dp phone
(7 chips + divider + 2×38dp icons ≈ 30dp per chip) the tile overflowed every chip and collided
with its neighbour — on the most-used context. Also `TextOverflow.Visible` on the label actively
spills into siblings in a shared row.
Fix: `BoxWithConstraints` inside `iOSToolbarItem` → `tileSize = (maxWidth - 6dp).coerceIn(22dp, 36dp)`
+ proportional glyph; label → `Ellipsis` + centred; chip gap 6dp → 4dp. Unbounded width still
resolves to 36dp. **Rule: never put a fixed-size child in a weighted Compose slot — measure it.**
Three tests now lock the width budget (≤7 chips, ≤8-char labels, ≤2 trailing icons).

### Audio toolbar deviation (documented, not faked)
Approved IA wanted 4 audio chips; only 2 shipped (`بیت`, `صدا`). `splitClip`/`deleteClip` touch

exist and ARE honoured by the exporter (`RenderGraphBuilder` → `RenderSegment` → `AudioFade`,
