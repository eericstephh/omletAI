## Round: aspect-ratio / orientation bug — diagnosis + fix

**Report (from the requester, non-technical):** portrait (9:16) imports show the right
dimensions and ratio; landscape (16:9) imports are "forced/stretched or cropped into
vertical dimensions".

### Diagnosis — read this before re-investigating

I swept the whole `app/src/main` tree myself **and** with a dedicated Explore agent.
**There is no code path in this repository that forces a landscape source into a portrait
frame.** That is a real finding, not a failed search, and it is worth stating precisely
because it constrains every future attempt:

- Exactly **one** `.aspectRatio(...)` exists in production: `EditorScreen.kt:2044`, fed by
  `canvasPreset.effectiveAspectRatio(sourceAspect)` where `sourceAspect` is
  `activeClip.width / activeClip.height` (`EditorScreen.kt:1078`). It is a pure pass-through.
- The foreground player is `RESIZE_MODE_FIT` (default `FillMode.FIT`) — it letterboxes and
  cannot stretch or crop.
- **Every fallback in the tree is landscape-biased**: `EditorUiState.canvasPreset`,
  `VideoProject.canvasPreset`, `ProjectEntity.canvasPreset`, `MIGRATION_4_5`'s
  `DEFAULT 'WIDE_16_9'`, `decodeCanvasPreset`'s `getOrDefault(WIDE_16_9)`, and every
  `ExportQuality` (`HIGH_1080P` = 1920×1080). A fallback can therefore only ever break
  **portrait**, i.e. the opposite of the report.
- `VERTICAL_9_16` is **never** assigned programmatically anywhere. Grep it: the only
  occurrence outside the enum itself is nothing. Same for `EditorVideoCanvas.CanvasAspect
  .Vertical(9f/16f)` (dead file, no call sites) and `AutoFrameSettings`' 9:16 default
  (reached only when the user explicitly runs Auto Frame).
- `EditorTimeline` has **no** thumbnail/bitmap pipeline (waveform + gradient placeholders
  only) — no Coil/Glide, no `getFrameAtTime` in the editor. So there is no fixed-cell
  filmstrip to blame.
- The asymmetry is therefore **not** producible by this Kotlin tree. The remaining variable
  is the container's own metadata (`METADATA_KEY_VIDEO_WIDTH/HEIGHT` vs `_ROTATION`), which
  is what the fix below hardens.

**The lesson, generalised:** the *direction* of a reported asymmetry is evidence. When the
user says "A is fine, B is broken", enumerate which mechanisms can produce that direction
before hunting for any mechanism at all. Half the candidates I found were ruled out purely
because they would have broken A instead of B.

### Real defects found and fixed (all in the four areas the requester enumerated)

1. **`VideoMetadataExtractor` trusted rotation metadata blindly.** Inline swap, untestable
   (needs a real `MediaMetadataRetriever`), no rotation normalisation, no guard.
   → New **`model/VideoDimensions.kt`** (pure, JVM-testable):
   `normalizeRotation` folds any degree value into `[0,360)` (`-90`/`450` were silently
   dropped by the old `== 90 || == 270`); `resolve(rawW, rawH, rotation, probeW, probeH)`
   swaps only for a real quarter turn, returns degenerate input **unchanged** instead of
   inventing a plausible pair, and accepts an optional **decoded-frame probe**. The probe is
   the decisive part: `MediaMetadataRetriever.getFrameAtTime` returns a **rotation-applied**
   `Bitmap`, so its orientation is ground truth. When it contradicts the metadata-derived
   orientation, the probe wins. This is the documented Android fragmentation where the
   retriever *already* folded rotation into the reported width/height — swapping again then
   flips an axis that was never rotated. Probe is advisory only: it can decide orientation,
   never pixel counts.
   `VideoMetadataExtractor` now takes one best-effort `getFrameAtTime` probe per import
   (wrapped in `runCatching`, falls back to metadata on failure).

2. **`CanvasPreset.forSourceDimensions()` was dead code.** Its KDoc says it "replaced the
   previous hard-coded `WIDE_16_9` project default"; it has **20 passing unit tests**
   (`CanvasPresetSourceDimensionsTest`) and **zero production call sites**. `createProjectFromClip`
   hard-coded `FREE` instead. → Both `InMemoryProjectRepository` and `RoomProjectRepository`
   now call `CanvasPreset.forSourceDimensions(clip.width, clip.height)`, so the first-import
   canvas genuinely adopts the clip's ratio. Canonical ratios snap to a preset (which also
   **pins the export frame**); non-canonical/unknown fall through to `FREE`.

3. **Hard-coded landscape canvas defaults.** `EditorUiState.canvasPreset` is what the
   preview reads *before* `loadProject()` overwrites it — a 16:9 there means the editor's
   first frame asserts landscape regardless of the import. → `EditorUiState`, `VideoProject`,
   `ProjectEntity` and `decodeCanvasPreset`'s fallback all changed to `FREE` ("track the
   source"), which is the only value that cannot be wrong about a source it has not seen.
   `MIGRATION_4_5`'s historical SQL is deliberately **left alone** — it already ran on
   installed DBs and rewriting it would diverge from those devices.

4. **FREE exports were framed landscape.** Both export entry points
   (`ExportDelegate.onExportClicked`, `EditorViewModel.onExportClicked`) used
   `if (preset.exportWidth > 0) preset.exportWidth else quality.widthPx`, and every
   `ExportQuality` is landscape — so a FREE portrait project had its captions and upscale
   grid laid out for 1920×1080 while a landscape project happened to be right. → New
   **`ExportFrame.resolveOutputSize`**: a sized preset wins; otherwise the source's own
   orientation decides, scaled to the tier's **long side** when it exceeds it, never
   upscaled, always even. Orientation-symmetric and budget-preserving by construction
   (landscape numbers are byte-identical to before).

### Corrected during the round (do not re-file)

**already** calls `persistProjectMeta()` two lines later (`EditorViewModel.kt:3840`). My

### Tests

New: `VideoDimensionsTest` (~28) and `ExportOutputSizeTest` (~19). Both pure JVM —
plain `Int`/`Float` only, per the `isReturnDefaultValues` trap. The load-bearing cases:
probe-disagrees-in-both-directions, degenerate metadata stays degenerate, and the
"swapping the source axes swaps the resolved output axes" symmetry property that makes a
tier preference for landscape unrepresentable.

Baseline was 1733 completed / 2 failed / 2 skipped; the 2 are the pre-existing

## Round: "App Update & Changelog Notification Bell" (🔔) — Home screen

**Ask:** bell in the Home TopBar → bottom sheet «تغییرات و آپدیت‌های جدید», with an
unread red dot that clears once the user views the latest update.

### Files

New: `model/AppUpdateInfo.kt`, `data/AppChangelogProvider.kt`, `data/AppUpdatePreferences.kt`,
`ui/screens/home/AppUpdateSheet.kt`, `test/.../model/AppUpdateInfoTest.kt`,
`test/.../data/AppChangelogProviderTest.kt`.
Changed: `model/HomeUiState.kt`, `viewmodel/HomeViewModel.kt`, `ui/screens/home/HomeScreen.kt`,
`settings/LocalizedStrings.kt`, `app/build.gradle.kts`.

### Decisions worth not re-litigating

- **The unread decision is a pure top-level `fun hasUnreadUpdates(current, lastSeen)` in
  `model/`**, not a method on the repository. `AppUpdatePreferences` needs a real `Context`
  (no Robolectric here) and `HomeViewModel` is a Hilt ViewModel with 2 ctor deps — both
  untestable on the JVM. This is the same seam the rest of the codebase uses; follow it.
- **`>` not `!=`.** The seen marker is written from the app's *current* version, so a
  downgrade or a restored backup carrying a higher marker must not relight the badge.
  `markUpdatesAsRead` also clamps with `coerceAtLeast` — the watermark only moves forward.
- **The badge clears on sheet *open*, and again from «متوجه شدم».** Both, because the spec
  says it clears "once the user views" it. Idempotent, so no latch is needed. `onDismiss`
  (back/scrim/swipe) deliberately does **not** un-read — that would need a backwards marker.
- **`AppUpdatePreferences` gets its own `SharedPreferences` file** (`app_update_prefs`), not a
  key in `SettingsRepository`'s `app_settings`. Preferences are what the user *chose*; this is
  a *bookmark* the app keeps about its own content. Different lifetimes.
- **The bell is a 38dp glass `Box` + `clickable`, NOT an `IconButton`.** M3 pins `IconButton`
  to a 48dp minimum interactive size, which would make it visibly larger than the two 38dp
  glass circles beside it (account, settings). `BadgedBox` wraps it and supplies the dot.
  This is the same trap as the weighted-slot one in MEMORY.md: a component's *minimum* size
  is not visible in its name.
- **`buildConfig = true` + `versionCode = 4` / `versionName = "1.4.0"`.** There was no
  hand-written `BuildConfig.kt` to conflict with. The changelog's newest entry is *typed by
  hand*, so `AppChangelogProviderTest` asserts it equals `BuildConfig.VERSION_CODE` /
  `VERSION_NAME.substringBefore('-')` — that test is the **only** thing binding the two, and
  it is the reason `currentVersionCode` reads `BuildConfig` rather than a copied literal.
  Bump the version without prepending a changelog entry → the suite fails, by design.
- `substringBefore('-')` strips the debug build type's `versionNameSuffix = "-debug"`
  (`app/build.gradle.kts:118`). Asserted rather than assumed, in case a version name ever
  legitimately contains a hyphen.

### Layout trap confirmed again (see MEMORY.md)

`AppUpdateSheet` uses `Column.heightIn(max = 620.dp)` so the `LazyColumn` inside can use
`weight(1f, fill = false)` and scroll while the footer stays pinned. Without the bound the
list measures against the sheet's unconstrained height and overflows. `fill = false` keeps a
short changelog from stretching the sheet to 620dp.

### Verified before writing (avoid the missing-import cascade)

`material-icons-extended` already a dependency; `PersianFont` is `model.PersianFont`
(`TextOverlay.kt:231`); `toFontFamily` is an **extension** `fun PersianFont.toFontFamily`
(`ui/screens/editor/PersianFonts.kt:26`) — a grep for `fun toFontFamily` returns nothing, so
search for the receiver when a symbol looks missing; `t()` is `ui/components/Localized.kt:16`;
all theme tokens (`LabelToolbar`, `HairlineSubtle`, `iOSShapes.capsule`) exist.

### The one thing that actually broke the build

`compileDebugKotlin` passed on the first try; **`compileDebugUnitTestKotlin` failed** with
`HomeViewModelTest.kt:36,43: No value passed for parameter 'appUpdatePreferences'`. A
pre-existing test constructed `HomeViewModel(repository)` and the new constructor dependency
broke it. **Lesson: adding a ctor dep to a ViewModel that already has a JVM test is a
source-breaking change to that test — grep `app/src/test` for the constructor before adding
the dep, not after the 3-minute build.**

The fix is the interesting part. `AppUpdatePreferences` needed a real `Context`
(`SharedPreferences`), which is unavailable in a JVM test here — so a concrete class would
have made `HomeViewModel` untestable and forced deleting the test. It became an
**interface + `DefaultAppUpdatePreferences` + `InMemoryAppUpdatePreferences`**, bound with
`@Binds` in `di/AppBindings.kt`. That mirrors `ModelInstaller → ModelManager` (the `Default…`
naming) and `ProjectRepository → RoomProjectRepository` (the `InMemory…` fake). **The
codebase's answer to "this dependency needs a Context" is an interface + in-memory fake, not
a mock and not `isReturnDefaultValues`.**

Explicitly rejected: making `prefs` null-tolerant (`runCatching { context.getSharedPreferences(...) }`)
so the test would pass on a stubbed `Context`. It compiles and it goes green, but it goes green
*for the wrong reason* and would silently drop the user's bookmark if `SharedPreferences` ever
failed on a real device. That is exactly the `isReturnDefaultValues` trap in MEMORY.md.

The refactor paid for itself immediately: `HomeViewModel` is now constructible in a test, so
`HomeViewModelTest` gained an end-to-end badge test (fresh install → unread; `markUpdatesAsRead()`
→ clear) that covers the ViewModel wiring `AppUpdateInfoTest` cannot reach.

### Result (verified)

`1807 tests completed, 2 failed, 2 skipped` — **1782 → 1807, +25, zero regressions**. The 2
failures are the two known asset-dependent ones (`RealModelInstallTest`,
`WhisperNativeSymbolsTest`); `grep -l "<failure"` over the result XMLs lists exactly those two
classes and nothing else. New/changed: `AppUpdateInfoTest` 9/0, `AppChangelogProviderTest` 15/0,
`HomeViewModelTest` 3/0 (was 2).

code** (same note as MEMORY.md). Run took 5m 35s this time, slower than the ~3 min baseline.

## Round: Tapsell ad SDK — "add it to the project" (it was already there)

**Ask (Persian):** add the Tapsell Plus / Mediation SDK, with an App Key + one Zone ID, detect
the stack, add the dependency + maven repo, initialise at startup, and put an ad in the export
flow.

### Diagnosis — Tapsell was ALREADY integrated. Do not re-add it.

Native Android Kotlin (Compose + Hilt + Media3) — not Flutter/RN. And the SDK was already in:

- `settings.gradle.kts:21` — `maven { url = uri("https://repo.tapsell.ir/repository/tapsell-plus-maven/") }`
- `app/build.gradle.kts:208` — `implementation("ir.tapsell:tapsell:1.4.0-alpha03")`
- `AndroidManifest.xml` — `INTERNET`, `ACCESS_NETWORK_STATE`, `com.google.android.gms.permission.AD_ID`
- `AICreatorStudioApp.onCreate()` — `tapsellAdManager.initialize()`
- `ads/TapsellAdManager.kt` + `ads/TapsellAds.kt` + a working app-open interstitial
- `HomeScreen.kt:107` — `showAppOpenOnce(activity)`

**Tapsell Plus is the deprecated predecessor of Tapsell Mediation.** The Plus artifact no
longer exists; `ir.tapsell:tapsell` is the Mediation facade and is what's installed. Never
"upgrade" this back to Plus.

**The only things actually missing were the real credentials and the export placement.** The
existing code shipped the literal placeholder `YOUR_TAPSELL_KEY`, which is why the whole
integration was inert. Verified end-to-end that the placeholder plumbing works: the merged
manifest at `app/build/intermediates/merged_manifest/debug/processDebugMainManifest/AndroidManifest.xml:95`
does contain `<meta-data android:name="ir.tapsell.mediation.APPLICATION_KEY" android:value="...">`,
i.e. the SDK's own manifest declares the `${TapsellMediationAppKey}` placeholder and Gradle
substitutes it. **That's how the SDK gets its key — not from `TapsellAds.APP_KEY`,** which only
feeds the `isConfigured` guard. Two values, one truth; they must be kept in sync by hand.

### The bug that would have silently broken the whole task

`TapsellAds.isConfigured` required **both** a real app key **and** a real app-open zone id:

```kotlin
get() = APP_KEY != "YOUR_TAPSELL_KEY" && INTERSTITIAL_ZONE_ID_APP_OPEN != "YOUR_ZONE_ID"
```

The requester supplied **one** zone id, for the **export** placement. Filling in only that
would have left `isConfigured == false`, so `initialize()` would return early and **nothing
would ever show — including the export ad they asked for.** Split it: `isConfigured` now means
"the app key is real, the SDK may initialise"; `hasAppOpenZone` / `hasExportZone` gate each
placement independently. A missing zone now disables exactly one placement.

### Once-per-process vs once-per-export — the whole reason for the refactor

`TapsellAdManager` had one `interstitialAdId` field, one `appOpenConsumed` flag, one `adState`.
Two placements cannot share those. It became a private `Placement(reuseAfterShow: Boolean)`
class with `appOpenPlacement(reuseAfterShow = false)` and `exportPlacement(reuseAfterShow = true)`,
plus one shared `requestAndShow(zoneId, slot, activity)` path.

The flag encodes the **only** behavioural difference between the two:

- app-open keeps its slot **consumed after a successful show** — once per process, by design.
- export **releases** its slot when the ad closes, so the next export can show again.

Both release when *nothing was shown* (request failed, show failed, Activity dying), so a
transient network failure never permanently burns a placement. `release(slot, wasShown)` is
the single funnel for that decision — a boolean, not three scattered `set(false)` calls.

Also added a cross-placement `AtomicBoolean showing` guard: two interstitials must never be on
screen at once and the SDK does not arbitrate that. Overlap is near-impossible in practice (an
export takes minutes, app-open resolves in seconds) but the failure mode is a crash.

`adState` is **still dead** — `grep -rn adState app/src/` outside the manager returns nothing.
With two placements a single shared flow can't describe both, so it's now documented as
diagnostic-only rather than pretending to be per-placement. A candidate for deletion.

### Hook point

`EditorScreen.kt` already had `LaunchedEffect(uiState.exportState)` with a
`rememberSaveable` `lastShownExportKind` de-dup guard that raises the result dialog on
`Succeeded`/`Failed`/`Cancelled` and resets on `Idle`. The export ad hangs off **that** branch,
gated to `Succeeded` only — no new effect, and the existing guard is what stops it firing on
every recomposition and across rotation. Fired from the screen, not inside `ExportDialog`, to
keep that dialog a pure function of its state.

### Flagged to the requester (unverified)

The supplied app key is **70 characters** (`gpperaotjlhstpjinpeqtsjmpqcdgkrothifljdgthfplnmmhkjbmprsqehstdcnlositc`);
Tapsell app keys are normally 32 lowercase alphanumerics. The zone id
`6abb735d3c315037c8c55b38` **is** a valid 24-char Tapsell ObjectId. Wired in as given, but a
wrong app key fails silently at runtime (init succeeds, no fill) rather than at build time —
worth confirming in the console.

### Follow-up: the 70-char key is CORRECT — do not "fix" it

The requester came back with "the correct key I found", and it is **byte-identical** to what was
already in both files (compared by length and exact string equality: 70 / 70 / 70, equal). So the
unusual 70-character length is **intentional**, not a truncated or duplicated paste. The earlier
"Tapsell keys are normally 32 chars" flag is resolved — leave the value alone. Both copies
(`TapsellAds.APP_KEY` and `manifestPlaceholders["TapsellMediationAppKey"]`) still have to move
together if it ever changes.

## Editor sub-panel height — compact CapCut-style layout

**Reported:** tapping any tool on the dock opened `SubPanelRow` at a flat 50% of the
editor height, squashing the video preview.

### Root cause

`EditorLayoutSpec.SubPanelHeightFraction = 0.5f`, consumed at exactly one place
(`EditorScreen.kt`, `.fillMaxHeight(...)` on the sheet's root `Box`). The sheet is a
non-weighted child of the root `Column` and the preview is the weighted one, so every
dp the sheet took came straight out of the preview. One fraction cannot serve both a
slider panel (wants ~170dp) and a gallery (wants ~340dp) *and* protect the preview.

### What changed

- **NEW `model/SubPanelHeight.kt`** — pure, JVM-testable policy: `Kind` COMPACT/GALLERY,
  `kindFor`, `fractionFor`, `minHeightDpFor`, `maxHeightDpFor`, `resolveHeightDp`.
  Plain floats in dp, never `Dp`/`Color`, because `isReturnDefaultValues` makes
  `android.*` inert in unit tests — a `Dp`-typed API would be asserted against `0f` and
  pass for the wrong reason. COMPACT is an explicit allow-list of 10 panels;
  **everything else defaults to GALLERY**, which fails safe: a too-tall slider sheet is
  untidy, a too-short gallery is unusable because its cards cannot be reached.
  `resolveHeightDp` = `(available × fraction).coerceIn(min, max)` then
  `.coerceAtMost(available − 180)`. That last clamp is applied last and **wins**, so the
  preview's floor beats the panel's own minimum on a tiny screen.
- **`EditorLayoutSpec.SubPanelHeightFraction` deleted** — verified first that it had
  exactly one consumer and zero test references.
- **`EditorScreen.kt`** — the sheet now measures itself with `BoxWithConstraints`.
  `maxHeight` there *is* the post-chrome space, because a `Column` defers weighted
  children and measures the sheet after the top bar and playback strip. That is why the
  budget can come from the real device instead of `LocalConfiguration`.
- **Animations** — the sheet is wrapped in
  `AnimatedVisibility(expandVertically(expandFrom = Bottom) + fadeIn(), shrinkVertically(shrinkTowards = Bottom) + fadeOut())`,
  and the timeline in the mirror-image Top-anchored pair. This finally makes the
  long-standing "slides up" comment true: there was previously **no** animation of any
  kind anywhere in `EditorScreen.kt`.
- **The exit-animation trap.** `if (toolPanel != null) { SubPanelRow(...) }` removes the
  sheet from composition in the frame the panel closes, so no exit transition can ever
  play. `SubPanelRow` now keeps a `lastPanelState` latch and renders
  `uiState.toolPanel ?: lastPanelState.value`. It also hands `SubPanelContent` a
  `uiState.copy(toolPanel = panel)`: `SubPanelContent` dispatches on `uiState.toolPanel`
  and several inner panels read it back, so without the copy the body blanks mid-collapse.

Numbers, asserted by the suite: compact is 26.6% of a 640dp screen / 26.4% of a 900dp one
(target ≤28%); gallery 33.3% / 35.2% (target ≤38%). The 180dp preview floor is never
breached across screens 600–1200dp × all 27 panels.

The drag handle and the 28dp close button **already existed** — that part of the request
was already satisfied.

### Trap worth remembering

Adding a nesting level around ~200 lines of existing code is not a reason to accept
wrong indentation. A 12-line Python script anchored on two unique lines (asserting each
matched exactly once) and prepending 4 spaces is faster and safer than hand-editing.
