# 2026-09-16 (later still) — Blocker #1 FIXED: multi-clip export

## The change
`export/VideoExportEngine.kt` used `graph.segments.first()`, silently discarding every clip after the first. Now every segment renders into ONE `EditedMediaItemSequence` wrapped in a `Composition`, laid end-to-end.

**Backward compatible by construction:** Media3 builds an equivalent single-sequence `Composition` internally for the old `start(EditedMediaItem, path)` overload, so a single-clip project takes an identical path.

## Media3 1.5.0 API verified BEFORE designing (via javap on the cached AAR — do this again, don't guess)
- `Transformer.start(Composition, String)` exists alongside `start(EditedMediaItem, String)`.
- `Composition.Builder(List<EditedMediaItemSequence>)`, `EditedMediaItemSequence.Builder(List<EditedMediaItem>)`.
- `EditedMediaItemSequence.Builder.addGap(long)` — unused so far (see gaps limitation).
- **`androidx.media3.effect.SpeedChangeEffect(float)`** and **`androidx.media3.common.audio.SpeedChangingAudioProcessor(SpeedProvider)`** exist — this is how per-clip speed gets baked.
- `EditedMediaItem.Builder` has **no** speed setter, so the effect + audio-processor pair is the only route.

## Subtitle rebasing trick
`SubtitleBurnInFactory.createOverlays` maps editor time → output time as `overlay.startTimeMs - clipTimelineStartMs`. Passing `segment.timelineStartMs - compositionOriginMs` makes it produce `compositionOrigin + (overlay - clipStart)` — the caption's position on the *composition* timeline. The factory is therefore reused **unchanged** per segment. For one clip the origin is 0, so the value is identical to before (backward compatible).

## Also fixed as a side effect
Progress previously used `totalOutputDurationMs` (the sum of ALL segments) while rendering only the first, so the bar could never reach 100%. Now correct.

## Files changed
- `export/RenderSegment.kt` — NEW fields `timelineStartMs`, `sourceWidthPx`, `sourceHeightPx` (all defaulted).
- `export/RenderGraphBuilder.kt` — populates them; normalises the `-1` auto-layout sentinel to 0.
- `export/VideoExportEngine.kt` — multi-clip Composition, per-segment AI pre-render with aggregated progress, per-clip speed baked (video + audio), FREE-canvas sizing for sequences, voice-clean post-pass gated to single-segment, class KDoc corrected.

- NEW test `export/CompositionTimelineTest.kt` (9 tests) + 3 tests added to `RenderGraphBuilderTest`.

# 2026-09-16 (latest) — Scoping the next task: Media3 per-frame hooks verified

## Media3 1.5.0 per-frame hook audit (read from the `-sources.jar` in the Gradle cache)

This is the deciding question for baking transitions/animation into the export. **Read the sources jar, it's in the cache — no guessing.**

| Hook | Signature | Per-frame? |
|---|---|---|
| `GlMatrixTransformation` | `float[] getGlMatrixArray(long presentationTimeUs)` | **YES** — "the frame with the given timestamp" |
| `MatrixTransformation` | `Matrix getMatrix(long presentationTimeUs)` | **YES** (default `getGlMatrixArray` delegates to it) |
| `TextureOverlay` | `int getTextureId(long)`, `Size getTextureSize(long)`, `OverlaySettings getOverlaySettings(long)` | **YES** — `OverlaySettings.alphaScale` is per-frame |
| `GaussianBlur` | `ConvolutionFunction1D getConvolution(long presentationTimeUs)` | **YES** |
| `GlEffect` | `GlShaderProgram toGlShaderProgram(Context, boolean)` | **NO timestamp** → `AlphaScale` and `RgbMatrix` are **static per instance** |

**Consequence:** per-frame *geometry* (scale/translate/rotate), per-frame *blur*, and per-frame *overlay alpha* are all natively reachable. But per-frame **RGB / alpha on the base layer is not** — `AlphaScale` on the base layer is also invisible anyway because the encoder writes no alpha channel. So a fade must be done as a full-frame solid-colour **overlay** (`OverlayEffect` + a 1×1 `BitmapOverlay`) whose `alphaScale` animates, not as a base-layer alpha.

Existing reusable machinery: `export/SubtitleBurnIn.kt` + `buildSubtitleOverlays(...)` already build `OverlayEffect`/`BitmapOverlay` chains, so the overlay route has precedent in-repo.

## RE-VERIFIED (my earlier audit claim was challenged and then confirmed)

**Transitions are write-only in the live preview — the audit was right.** I initially suspected the claim was too strong because `EditorVideoCanvas.kt:142-183` computes a `TransitionPose` and applies it (including explicit white/black flash overlay `Box`es). But:

- `EditorVideoCanvas` has **no call sites** — the grep returns only its own definition. `CanvasSurface` is `private` and only called from inside it. It is orphaned code.
- The live preview is `EditorScreen.EditorVideoPreviewSection` (EditorScreen.kt ~1548+), which renders `PlayerView` via `AndroidView`.
- That section applies **`animPose`** (`motionPoseAt(animation, animT)` — i.e. `ClipAnimation`, not transitions) plus `opacity`, merged in one `graphicsLayer` at EditorScreen.kt:1942-1961:
  `alpha = (animPose?.alpha ?: 1f) * opacity.coerceIn(0f, 1f)`
- `EditorScreen` never reads `transitionIn`/`transitionOut` — they only appear as `onSetTransition` parameters handed to `TransitionPanel`.

**So: the live preview already has a working per-frame pose pipeline, and transitions simply aren't plugged into it.** Adding transitions to the *preview* is therefore a small change (merge `TransitionEngine.poseForCurrentPosition` into the existing `animPose`), independent of the much harder export baking.

## Field-consumer audit (write-only fields confirmed)

# 2026-09-16 (final) — Transitions now render: preview AND export

User picked "Transitions, preview + export" from the offered menu. This closed the last major write-only feature: the 43-transition library and the Transition panel are no longer decorative.

## Design: additive by construction
A `null` transition config appends **nothing** to the effect list, so a project with no transitions exports byte-identically to before. This was the explicit safety requirement.

## New file: `model/TransitionGeometry.kt` (pure Kotlin, ~230 lines)
The single bridge that lets preview and export agree on what a pose means. Unit-testable with no device and no GL context.

- `REFERENCE_WIDTH_DP = 430f`, `REFERENCE_HEIGHT_DP = 280f` — derived from the engine's own constants (`PUSH_LEFT/RIGHT = ±430f * a`, `PUSH_UP/DOWN = ±280f * a`, i.e. one full frame at full intensity).
- `matrix(pose, aspectRatio): FloatArray` — column-major, ready for `gl_Position = uTransformationMatrix * aFramePosition`.
- `frameAlpha`, `blackoutAlpha`, `whiteoutAlpha`, `blurSigmaPx(pose, outputHeightPx)`.
- `needsBlur` / `needsWhiteOverlay` / `needsBlackOverlay` — **probe** the pose across the window (`OVERLAY_PROBE_SAMPLES = 16`) instead of matching on type names, so a newly added `TransitionType` is covered automatically with no second place to update.

**Critical coordinate facts, read from the actual shader — not assumed:**
- Media3's vertex shader (`assets/shaders/vertex_shader_transformation_es2.glsl` in the AAR) does `gl_Position = uTransformationMatrix * aFramePosition;` and texture coords `aFramePosition.y * 0.5 + 0.5` → **NDC positive Y is UP**, frame top is `y == +1`. The caller must negate Y itself.
- `MatrixUtils.getGlMatrixArray(android.graphics.Matrix)` is a straight row-major→column-major transpose with **no** y-flip.
- `ScaleAndRotateTransformation.configure` aspect-corrects with `preScale(aspect, 1)` … `postScale(1/aspect, 1)` to stop rotation shearing. Copied that pattern.
- `blackoutAlpha = max(1 - frameAlpha(pose), flashBlack)` — folds the fade ramp and an explicit black flash into one pass, because **MP4 has no alpha channel**.

## Pre-existing bug found and fixed: OUT-transition progress was inverted
`poseForCurrentPosition` originally computed the OUT window progress as `(clipDurationMs - localMs) / outWin`, i.e. **1 → 0**. But `evaluate()`'s OUT branch is `a = eased`, documented as "starts at identity and grows to the extreme" — it needs **0 → 1**. The effect was that `FADE_OUT` behaved *identically* to `FADE_IN`, and every leaving transition ran backwards.

Invisible for as long as nothing rendered transitions at all; visible the moment preview and export started honouring them. Fixed rather than encoded into the tests.

Also extracted a shared `poseForClipLocal(clipLocalMs, clipDurationMs, transitionIn, transitionOut)` — the single source of truth both renderers call, so they cannot drift. `poseForCurrentPosition` now delegates to it. In/Out overlap resolves in favour of In, matching the original preview behaviour.

## Preview (`ui/screens/editor/EditorScreen.kt`, ~4900 lines)
1. New `transitionPose` block after `animPose`, using `remember(sourceClip?.transitionIn)` for the decoded configs and `TransitionEngine.poseForClipLocal(clipLocalMs = currentPositionMs - clipTimelineStartMs, …)`.
2. The existing `graphicsLayer` now composes `transSx`/`transSy`, adds `TransitionGeometry.translationFractionX/Y(pose) * size.width/height`, adds `transitionPose.rotationZDeg`, and multiplies alpha.
3. New "Layer 2.4: transition flash overlays" — two `Box`es (`Color.Black` / `Color.White`) at `flashBlack`/`flashWhite` alpha, gated at `> 0.01f`.

## Export: new file `export/TransitionEffects.kt` (~280 lines)
`internal object TransitionEffects` → `build(segment, outputWidthPx, outputHeightPx): List<Effect>`.
- `PoseTimeline` — shared pose resolver, feeds all three effects.
- `TransitionMatrixEffect : GlMatrixTransformation` — implemented **directly**, not via `MatrixTransformation`, and returns `Size(inputWidth, inputHeight)` unchanged from `configure`. That makes Media3 **clip** the overflow instead of growing the frame — the opposite of `ScaleAndRotateTransformation`'s convention, and the behaviour a push/slide needs.
- `TransitionBlurEffect : SeparableConvolution()` — sigma floored to `MIN_SIGMA_PX = 0.1f` because `GaussianFunction` is `checkArgument(sigma > 0 && …)`. (`GaussianBlur` is `final`, hence the subclass of `SeparableConvolution`.)
- `TransitionFlashOverlay : BitmapOverlay()` — lazily-created solid-colour bitmap, per-frame `setAlphaScale`.
- **`TextureOverlay` is NOT an `Effect`** — it is a component of `OverlayEffect`, which IS. The two washes therefore go into one `OverlayEffect(washes)`.

# 2026-09-16 (last) — `UpscalerExportEngine` fixed: multi-clip + the upscale that never happened

The last engine carrying the `segments.first()` bug class. Two distinct defects, both confirmed by reading rather than assuming.

## Defect 1 — only the first clip rendered
`UpscalerExportEngine.kt:118` called `graph.segments.first()` and rendered one `EditedMediaItem` via `transformer.start(editedMediaItem, path)`. Now every segment goes into ONE `EditedMediaItemSequence` wrapped in a `Composition`, exactly the shape `VideoExportEngine` uses. Single-clip projects take a behaviourally identical path (Media3 builds that Composition internally for the old overload).

## Defect 2 — the upscale never happened
`preset.targetScale` reached **nothing**:
- `effectiveConfig` was computed with `outputWidthPx/HeightPx = base × targetScale`, then passed to `OutputTarget.create(context, config, segment)` — which uses only `config.outputBaseName` — and to `buildEditedMediaItem(segment, settings, config)`, which **never referenced its `config` parameter at all**.
- `Transformer` exposes **no "set output resolution" API**; the output frame size is decided by the effect chain. So `ULTRA_4K` produced a source-resolution file.

Fixed by pinning the size with `Presentation.createForWidthAndHeight(w, h, LAYOUT_SCALE_TO_FIT)` as the last effect in each item's chain. That is the only mechanism that actually resizes the output.

## Which dimensions get multiplied — got this backwards once
My first pass sized from `source dims × targetScale` (reading `UpscalerSettings.kt:21-23`, "relative to the source"). Wrong. `EditorViewModel:3774-3786` deliberately resolves `config.effectiveWidthPx/HeightPx` from the **canvas preset**, falling back to `UpscalerExportPresets.forPreset(preset).effectiveWidthPx`, and passes it in — the canvas/aspect choice is the caller's contract. Sizing from the source would have silently discarded a 9:16 or 1:1 canvas.

**Correct contract: caller's target frame × `targetScale`**, source dims as fallback only. `EditorViewModel` comment is authoritative here; `UpscalerPreset`'s KDoc is not.

Consequences worth knowing (pinned in tests):
- 9:16 canvas (1080×1920) + `ULTRA_4K` → **2160×3840** (portrait 4K).
- FREE canvas + `ULTRA_4K` → base is `ExportQuality.ULTRA_4K` (3840×2160) → ×2 → **7680×4320, i.e. 8K**. That is the author's intent (`UpscalerExportPresets.outputBounds` documents "cap at 8K"), and 8K encoding will fail or fall back to software on most devices — flagged to the user, not silently changed.

## New pure helper: `UpscaleOutputSize`
`internal object` in the same file, no Android/Media3 types, so it is JVM-testable (this project has no Robolectric/mocking). Does the scale + 8K clamp + even-rounding:
- **One shared `capFactor`** so a frame that overshoots the ceiling shrinks uniformly instead of being squashed on one axis.
- **`even()`** rounds *down* and floors at 2: H.264 in yuv420p needs even dimensions, and `even(1)` would otherwise yield 0.

## Files changed
- `export/UpscalerExportEngine.kt` — multi-clip sequence, `Presentation` sizing, `UpscaleOutputSize`, corrected class KDoc (v1 claims replaced with the real v2 behaviour + honest limitations).
- NEW test `export/UpscaleOutputSizeTest.kt` (**14 tests**).

`testDebugUnitTest` → **BUILD SUCCESSFUL in 2m 15s**, **902 tests, 0 failures, 0 errors, 84 suites** (was 888).

# 2026-09-16 (final+) — Audio fade in/out now actually renders (preview + export)

`fadeInMs` / `fadeOutMs` were the last confirmed write-only pair: `AudioPanel` sliders → `EditorViewModel.setClipFadeInMs/Out` → persisted in `EditorStateJson`, read by **nothing**. Now baked into the export *and* audible in the preview.

## New pure helper: `model/AudioFade.kt`
`gainAt(clipLocalMs, clipDurationMs, fadeInMs, fadeOutMs): Float` — linear in **amplitude** (matching the `AudioClip` KDoc "linear fade-in duration"). Both renderers call it, so the preview and the exported file cannot drift.

- Windows are **clamped to the clip**, so a fade longer than the clip spans it instead of stalling at partial gain. (Needed: `EditorViewModel` clamps against `effectiveDurationMs`, which ignores `speed`, while the export measures against the speed-adjusted `outputDurationMs`.)
- **Overlapping windows → `min()` of the two gains**, so the clip ducks in the middle instead of one fade silently cancelling the other.
- NaN position → unity (the preview feeds this from a player clock; a NaN must not silence the clip).
- `isIdentity()` lets both callers skip the work entirely when no fade is set.

## Export
- `RenderSegment` gained `fadeInMs` / `fadeOutMs` (defaulted, so nothing else had to change); `RenderGraphBuilder` populates them.
- New `FadeAudioProcessor : BaseAudioProcessor` in `VideoExportEngine.kt`, modelled on the existing `VolumeScalingAudioProcessor`.
- **Clip-local time is tracked by counting input frames** — `AudioProcessor.queueInput` carries no timestamp at all. Exact for a linear export because the processor is constructed per segment; `onConfigure` / `onFlush` / `onReset` restart the clock.
- **Appended LAST** in `buildAudioProcessors` so it sees post-speed audio: the counted clock is then in output time, matching `outputDurationMs`. The volume and speed processors are time-invariant so their order is free.
- Gain is computed **per sample**, not per buffer, so the ramp is sample-accurate rather than stepping in ~20 ms chunks.

## Preview
- **`EditorScreen`: the 33 ms poller is now the SOLE writer of `exoPlayer.volume`.** The existing volume/mute `LaunchedEffect` writes a `baseVolumeRef` instead of touching the player. This deliberately avoids the two-writers bug that silently broke playback speed earlier — whichever effect ran last would win.
- The poller's `Runnable` is created once, keyed on `exoPlayer`, so composition values captured in it are frozen (the trap already documented at `EditorScreen.kt:412`). The fade config therefore reaches it through four `remember`ed states: `fadeClipStartRef`, `fadeClipDurationRef`, `fadeInRef`, `fadeOutRef`, refreshed by a `LaunchedEffect` keyed on the fade fields so dragging a slider is heard immediately.
- Time base: `pos` is the **same clock the timeline shows** (`exoPlayer.seekTo(target)` is fed timeline positions, and `setMediaItem` uses no clipping), so `clipLocalMs = pos - clipStart` — the convention the transition pose already uses.
- `AudioMixerPlayer.StemClip` gained `fadeInMs` / `fadeOutMs`; `syncTo()` applies `base * gain` per stem each tick, so audio-only clips fade too.

# 2026-09-16 (last) — Multi-track audio: audio-only clips now mixed into the export

The gap flagged in the entry above. `RenderGraphBuilder` filtered `!it.isAudioOnly`, so an imported song played in the editor and **vanished from the exported MP4** — silent content loss.

## Media3 semantics verified from the sources jar FIRST (not assumed)
- `Composition.sequences`: *"MediaItem instances from different sequences that are overlapping in time will be **mixed** in the output."* → extra sequences are the mixing mechanism.
- `EditedMediaItemSequence`: *"instances in a sequence **don't overlap in time**."* → this is why one sequence per clip is required, not one sequence for all audio.
- `EditedMediaItemSequence.Builder.addGap(long)`: *"Gaps are only supported in sequences of audio."* → legal here, illegal in the video sequence.
- **UNITS TRAP:** `addGap`'s KDoc says *"in milliseconds"* but its body forwards the value straight to `EditedMediaItem.Builder.setDurationUs(long)`, which is documented in **microseconds** and asserts `durationUs > 0`. So the code multiplies by 1000, and never emits a zero-length gap (it would throw). Passing ms directly would have made every gap 1000× too short.
- `EditedMediaItem.Builder.setRemoveVideo(boolean)` exists and is used — an `isAudioOnly` clip can still point at a container carrying a video track, which would otherwise contribute a second video stream.

## New pure helper: `CompositionTimeline.outputMsForTimelineMs(segments, timelineMs)`
Maps an editor-timeline position onto the composition timeline, so a clip the user placed at T in the editor lands at the right moment in the file. Piecewise-linear:
- inside segment *i* → `origin(i) + progress * outputDuration(i)`
- in a gap → the next segment's origin (gaps are not reproduced)
- past the end → the composition's total duration

`progress` is measured against the segment's **editor** span (`sourceDurationMs`, i.e. the clip's `effectiveDurationMs`, which ignores speed) and applied to its **output** span. Those differ when `speed != 1`, and mapping proportionally is what keeps a 2× clip's midpoint on the midpoint of its output segment.

## Design decisions
- **One Media3 sequence per audio clip**, each `[gap(startMs), item]`. Separate sequences may overlap and get mixed, so this handles "music + SFX at the same instant" with no overlap analysis at all.
- **Audio is clamped to the video's length.** `totalOutputDurationMs` stays video-only, so adding a long music track cannot silently extend the exported video.
- `setRemoveVideo(true)` on every audio item, and no video effects.
- A clamped audio item re-derives its segment (`copy(sourceEndMs = endMs)`) before building the audio chain, so `FadeAudioProcessor` measures its fade-out against the audio that will actually be written rather than being cut off mid-ramp.
- A project containing only audio still returns `NoRenderableClips` — an MP4 needs a video track.

# 2026-09-16 (last++) — `ClipTransform` now fully baked: the Transform panel's pan and zoom

The Transform panel's `scale` and `offsetX`/`offsetY` were the next two write-only fields. They turned out to be **one task, not two**, because of a defect found while scoping.

## Decisive finding — `ScaleAndRotateTransformation` silently neutralizes a uniform scale

Read from `media3-effect-1.5.0-sources.jar` (`ScaleAndRotateTransformation.java:123-160`), not guessed:

```java
adjustedTransformationMatrix.preScale(inputAspectRatio, 1f);
adjustedTransformationMatrix.postScale(1f / inputAspectRatio, 1f);
// … map the 4 NDC corners, take the bounding box …
float scaleX = (maxX - minX) / GlUtil.LENGTH_NDC;   // LENGTH_NDC == 2
adjustedTransformationMatrix.postScale(1f / scaleX, 1f / scaleY);
return new Size(Math.round(inputWidth * scaleX), Math.round(inputHeight * scaleY));
```

It deliberately **grows the frame** so that no input pixel is lost, and divides the scale back out of its own matrix. The downstream `Presentation(LAYOUT_SCALE_TO_FIT)` then scales that frame back to the canvas — **exactly undoing the user's zoom**. Dragging the zoom slider changed nothing in the exported file. And the pan had no route at all (no translation primitive).

Worked the flip case through the same code to be sure it was safe to keep there: a pure flip (`scaleX = -1, scaleY = 1, rot = 0`) maps the NDC square back onto itself, so the bounding box is `(-1..1)`, `scaleX = scaleY = 1`, `configure` returns the **input** size and the matrix stays a pure ±1 flip. With the old `-t.scale` encoding the `s` cancelled entirely, which is why removing it changes nothing for flips.

## Why the split is mathematically free (the part worth not re-deriving)

`scale` + pan move into the pose (a `GlMatrixTransformation` reporting the *input* size, so Media3 **clips**); `rotation` + flip stay in `ScaleAndRotateTransformation`. The export composite is therefore

`T · R_pose · S_zoom · P · R_transform · S_flip`, and with `P` and `S_zoom` uniform this collapses to `T · R(θ_pose+θ_tr) · diag(f·s, g·s)` — **identical** to the preview's single `graphicsLayer` matrix, which folds the flip into `scaleX`. Uniform scale commutes with both the rotation and the ±1 flip, so the two orders agree. Verified against the preview at `EditorScreen.kt:2056-2089`.

**Effect order is load-bearing.** The chain is `Speed → ScaleAndRotateTransformation → GradeRgbMatrix → Presentation → ClipMotionEffects → subtitles`, so `ClipMotionEffects` runs **after** the `Presentation`. That is what puts the pose in canvas space (so the pan's canvas-fraction units mean the same thing in both renderers) and the flip *inside* the pan rather than mirroring it. Nothing needed reordering.

Pan is converted with `panX * TransitionGeometry.REFERENCE_WIDTH_DP` so it shares the translation field; the round trip back through `translationFractionX` is asserted in tests. Non-finite/non-positive scale → `1f`; non-finite pan → `0f`.
- `export/ClipMotionEffects.kt` — `build()` computes `hasTransform` and gates the early return on `hasGeometry || darkens`; the matrix effect is added when `hasGeometry` (transition **or** preset **or** transform), so a merely-translucent clip still gets only the wash. `PoseTimeline` and `ClipMotionMatrixEffect` take the three new inputs; the blur pass leaves them defaulted.

# Sharpness — the grade panel's last write-only *Detail* control

`ColorGrading.sharpness` was write-only: `ColorGradingPanel.kt:331-369` wrote it, the DB persisted it, and no renderer read it back (`grep -rn "\.sharpness" main/java` → only the two panel lines that feed the slider itself). It cannot ride the 4×5 grade matrix — a sharpener reads neighbouring pixels, and a colour matrix is a per-pixel transform by construction — so it is now a real separable convolution in **both** renderers.

## Mechanism, verified from the artifacts (not guessed)

`androidx.media3.effect.SeparableConvolution` is an **abstract class**, not a factory: subclass it and return a `ConvolutionFunction1D` per frame. The no-arg constructor defaults `scaleWidth`/`scaleHeight` to `1`, so the pass is **frame-size-preserving** — mandatory here, since the muxer rejects a mid-stream dimension change on the single video track it writes.

The load-bearing discovery is in `SeparableConvolutionShaderProgram` + `fragment_shader_separable_convolution_es2.glsl`:

- The function is **not** called once per tap. It is **rasterised into a 1-D lookup texture** at `RASTER_SAMPLES_PER_TEXEL = 5` samples/texel, and the shader samples that LUT with **`GL_LINEAR`** — so each tap is the **average of an adjacent sample pair**.
- With domain `[-1.5, 1.5]` the raster is `ceil(3*5 + 2*5) = 25` texels with samples on `-1.5 + i*0.2`, and the lookups for source-texel offsets `-1, 0, +1, +2` land **exactly half way between two adjacent samples**: `±0.9/±1.1`, `±0.1`, `±1.9/±2.1`.
- Therefore the kernel is exact **only if `value()` returns the same number for both members of every pair** — which is why the weight function is a **step function with breakpoints at 0.5 and 1.5**, sitting deliberately *between* the sampled positions. A continuous kernel (linear, Gaussian) would be sampled off-centre and come out attenuated.
- The shader **normalises by the accumulated weight** (`gl_FragColor = accumulatedRgba / accumulatedWeight`) and clamps its support window to the frame (`max(0, ...)`), so borders renormalise correctly instead of darkening.
- The shader program re-uploads the LUT only when the returned function stops comparing `equals`, so the effect caches one value-equal instance per strength. A slider drag therefore costs one small texture upload, **not** a pipeline rebuild — the same trick `GradeRgbMatrix` uses for the colour matrix.
- Texture wrap is `GL_CLAMP_TO_EDGE` (verified in `media3-common`'s `GlUtil.bindTexture`), so the out-of-range `+2` tap reads the zero padding rather than wrapping around.

## The kernel, and what it cannot be

1-D `h = [-k, 1+2k, -k]`; the two passes yield the outer product `h ⊗ h` — the classic 3×3 sharpen with its **corners filled in**. The cross-shaped `[[0,-k,0],[-k,1+4k,-k],[0,-k,0]]` has **matrix rank 2 and is therefore not separable**, so it is unreachable through this API at all. That is documented in the KDoc rather than silently shipping a different kernel. The weights sum to 1, so flat regions are untouched (asserted by test); the support is 1 texel, so the halo radius is 1 pixel at whatever resolution the pass runs at.

## Changes
- NEW `model/SharpnessKernel.kt` — pure: `isActive`, `weight` (0..1 → 0..0.5), `taps`, `tapSum`, `value`, plus `SAMPLE_POSITIONS` which pins the derived raster pairs so a test asserts the pairing invariant directly instead of trusting the comment.

# Vignette — the next three write-only fields

`vignetteAmount` / `vignetteFeather` / `vignetteRoundness` were write-only in exactly the same way as `sharpness`: `ColorGradingPanel.kt:343-357` wrote them, the DB persisted them, and nothing read them. The falloff maths existed all along as `ColorGradingMath.vignetteFactor`, but that helper had **zero call sites** — so it was deleted (moved) and the maths now lives in `model/VignettePlate.kt`, actually used.

## Mechanism, verified from the artifacts

A vignette is a function of **position**, not colour, so like sharpness it cannot ride the 4×5 matrix. It is a Media3 `BitmapOverlay`: a bitmap whose alpha is the strength and whose RGB is the colour blended toward.

The blend is **straight (non-premultiplied) alpha** — `insert_overlay_fragment_shader_methods.glsl`:

```glsl
outputColor.rgb = overlayColor.rgb * overlayColor.a + videoColor.rgb * (1.0 - overlayColor.a);
```

So a **black** plate darkens (`video * (1-a)`) and a **white** plate brightens (`a + video*(1-a)`). That is how one code path serves the model's documented `-1 brighten .. +1 darken` range: the **sign picks the plate colour, the magnitude picks the alpha**. The retired `vignetteFactor` returned `1 - amount*falloff` and short-circuited to `1f` for `amount <= 0`, i.e. it could only ever darken; `alphaAt` is the same curve expressed as an alpha, so the darkening is bit-for-bit what that helper described.

### The overlay is NOT stretched to fill the frame

`OverlayMatrixProvider.getTransformationMatrix` reduces to `T = aspectRatioMatrix * scaleMatrix` for default anchors/rotation (the `overlayFrameAnchor`/`scaleInv` pair and the `overlayAspectRatio` pair around an identity rotation both cancel), i.e. the overlay quad is scaled by `(ow/W * sx, oh/H * sy)`. With the default `scale = (1,1)` an overlay is drawn at **its own pixel size**, centred — so a quarter-size plate would appear as a small vignette in the *middle* of the frame, not as a full-frame one.

`overlayScale` fixes that by asking `setScale` for exactly `frameSize/plateSize`. Consequence worth knowing: plate pixel `(x,y)` then lands on frame position `(x/pw, y/ph)` **exactly**, so the falloff is evaluated at the same normalised coordinate no matter the plate resolution. **Plate resolution is a quality choice, never a shape choice.**

### Under-covering is the dangerous direction

`getClampToBorderOverlayColor` returns `vec4(0,0,0,0)` — i.e. **no effect** — for texture coords outside `[0,1]`. A plate that comes up short therefore leaves an un-darkened border, most visible at the corners where the vignette is strongest. Over-covering is free (the extra is never sampled), so `OVERCOVER = 1.01f` deliberately errs that way. `plateSize` also floors at 2px and collapses unknown frame dims to a 1×1 transparent plate — a no-op, not a crash.

### No size has to be passed in

`TextureOverlay.configure(Size)` is called by Media3 with the real frame dimensions before the first draw and again on any change. So this pass needs **no `frameIsKnown` guard** — unlike the fade washes, whose size the engine has to guess (and which degrade to a cut in the FREE-canvas + rotation case). Verified from `OverlayShaderProgram.drawFrame` that `getTextureId` is called **before** `getTextureSize`, which matters because `BitmapOverlay.getTextureSize` does `checkNotNull(lastBitmap)` — a subclass must not assume the other order.

### Why the plate is only 1/4 resolution

A vignette is a low-frequency gradient, so a 270×480 plate stretched over 1080×1920 is visually indistinguishable from a full-resolution one and GL's linear filtering interpolates it back. That makes a slider drag ~1 ms of maths plus one 0.5 MB upload instead of ~30 ms plus 8 MB. **The same trick is unavailable for grain**, because grain is high-frequency — it would come out as soft blobs.

## Two test failures, both mine, both instructive

`more feather softens the falloff` and `the visible multiplier darkens monotonically outward` failed on first run. **The implementation was right; my sample points were wrong.** At feather 0 the clear core reaches `d = 0.80` and at feather 0.5 it reaches `d = 0.625`, so points I expected to be "mid-ramp" were inside the flat core and read exactly 0 / exactly 1 — comparisons that can never discriminate. Rewrote them: sample **along the diagonal** (the x-axis only reaches `d = 0.75`, so it samples core-then-corner and nothing between), and measure "softer" as the **steepest step across the ramp** rather than the value at one point. Checking this also exposed a real **documentation** error — `feather` *narrows* the clear core while *widening* the ramp, so it makes the vignette softer *and larger*, not simply weaker. The KDoc had claimed it widened both.

# `canvasBackground` — the last write-only field (2026-09-16, later)

`CanvasBackground.SolidColor` now reaches the exported file. `Blur` does not, and the reason is structural rather than lazy (see below). The earlier "blocked" verdict on this field was **half right**: `Presentation` still has no background-colour overload, but that only rules out the *obvious* route, not every route.

## The decisive fact came from the preview, not from Media3

`EditorScreen` puts the letterbox colour on the **outer canvas `Box`** (`.background(letterboxColor)`) and the per-clip pose on the **inner foreground `PlayerView`** (`graphicsLayer { scaleX/scaleY/translationX/rotationZ/alpha }`). So the background is **static in canvas space while the video moves over it**. Everything about this pass follows from that one fact, and getting it backwards produces a plausible-looking design that is wrong in both directions.

## Why the plate cannot go *before* the pose

The tempting design: put the plate between the `Presentation` and the pose, so the pose transforms the plate and the video together and the hole tracks the silhouette for free. **The hole does track, but the outer bounds move too** — a pose is a rigid transform, so it translates and scales the plate's *frame* as well as its hole.

- `ClipMotion.ZOOM_IN_START_SCALE = 0.45`, so a zoom-in clip starts with the plate covering 45% of the canvas.
- A push transition translates by a full frame width (2 NDC units).

Covering the worst case needs a drawn plate about 10× the canvas in each axis (≈ 10 800 × 19 200 px at 1080p) — past the GL maximum texture size on most devices and ~800 MB of ARGB. Over-covering is not a viable escape hatch; the correct answer is the opposite arrangement.

## Why the plate *is* the right answer after the pose, and why it has to be per-frame

Placed **after** `ClipMotionEffects`, the plate stays canvas-static and the *hole* is what moves — which costs nothing because the hole is recomputed from the pose anyway. The pose is available at the same call site: `PoseTimeline` (now `internal`) evaluates it, and `CanvasLetterbox.posedCorners` maps the un-posed `videoRect` through exactly the same arithmetic `TransitionGeometry.matrix` bakes, so the plate's edge and the video's edge cannot drift apart.

Two placements matter as much as the one above: **after** the `Presentation` (the bars do not exist before it) and **after** the washes (on screen a fade dims the video toward the background and leaves the bars alone, which repainting the bars after the full-frame black wash reproduces exactly).

## A per-pixel mask is impossible here; a scanline rasteriser is not

The obvious implementation — invert the pose per pixel and test containment — is **~2.1 M pixels × ~15 scalar float ops at 1080p**, i.e. tens of millions of ops per frame. ART does not vectorise that: it is 30–90 ms per frame, more than a 30fps budget on its own. The silhouette is a **convex quadrilateral**, though, so `rasterise` intersects its four edges with each row's centre line once (O(height), ~20 flops/row) and memfills the pixels whose centres fall inside. Per frame that is one memfill plus a few thousand flops; the caller caches on the pose, so a static clip pays it once and an animated one pays ~1–2 ms.

## The mask is binary on purpose, and that is not a shortcut

I first wrote horizontal coverage-based anti-aliasing, then removed it. **A coverage ramp is worse here, not better.** The video's edge is rasterised by GL with one sample per pixel, so a half-transparent mask pixel shows as a 50% colour wash straddling an edge that is actually hard — a visible fringe on the video and a dark sliver on the bar. Matching GL's **pixel-centre rule** is what keeps the two coincident: the plate's boundary then lands on the *same pixels* as the video's own edge, including on a rotated silhouette where both produce the identical staircase.

Both axes use the **half-open ("top-left") fill rule** — a centre landing exactly on the far edge counts as outside. The first version had a closed x-interval and a half-open y test, which disagreed by one pixel only when a coordinate was exactly an integer; the test `a pixel centre exactly on the far edge counts as outside` now pins both axes. The two rules only ever differ on exactly-integer coordinates, so the cost of the stricter one is nil.

## A non-finite pose input does not fail loudly — it fails *invisibly*

Found by a test, not by inspection, and worth remembering: a NaN anywhere in the pose makes `contains` report "outside" for every point (so `coversCanvas` says "no bars") **and** makes `rowSpan` report no crossing for every row (so nothing is punched out). The result is a plate that is **fully opaque** — the whole frame painted in the background colour with the video hidden underneath. Every pose input is therefore sanitised to its identity value in `posedCorners`. The test that caught it asserts a NaN rotation reads as no rotation.

## `videoRect` no longer means "are there bars"

It used to return `null` when the video covered the canvas, and that signal was load-bearing. It is wrong once a pose exists: a clip whose source matches the canvas aspect has no bars at rest, but `ZOOM_IN` shrinks it to 45% on the first frame and exposes them. So `videoRect` now reports the whole canvas in that case, `FillMode.FILL` is no longer rejected, and the "are there bars" question moved to `needsPlate`, which tests the **posed** silhouette. `CanvasBackgroundOverlay.build` still refuses the pass for a clip that *cannot move* and already covers the canvas — that check needs the expected frame size, which is why the engine passes `outputWashPx` in.

## Two API details that bit

- `CanvasBackgroundOverlay` had to become **`internal`**: its constructor takes the now-`internal` `PoseTimeline`, and Kotlin rejects a public function exposing an internal parameter type. Making `PoseTimeline` public would have been the wrong trade.
- The overlay's `setScale` must key off the **bitmap's** dimensions, not the frame's. They are equal for the canvas-sized plate and differ by `frameWidth×` for the 1×1 transparent stand-in; conflating them silently makes the stand-in's scale wrong (harmless today, a trap tomorrow).

## Refactor: one pose, one construction

`ClipMotionEffects` now owns `hasGeometryPose(segment)` and `geometryPoseTimeline(segment)`, and `ClipMotionMatrixEffect` takes a `PoseTimeline` instead of rebuilding one from eight parameters. The plate and the matrix must agree frame for frame, so they share one evaluator and one construction rather than two copies that drift.

## Deliberate gaps, documented not hidden

- **`Blur`** is still preview-only. It is a *second video layer* (the preview stacks a second `PlayerView` with `RESIZE_MODE_ZOOM` + `Modifier.blur(36.dp)`), which needs a `Composition` with two sequences and a `VideoCompositor` — a timeline-model change, not a field.
- **A fade still washes toward black, not toward the bars.** `ClipMotionWashOverlay` folds the fade family, the fading presets, `opacity` and explicit `flashBlack` into one black pass, which is exactly right on a black canvas and slightly wrong on a coloured one: at the trough the bars stay the chosen colour while the video dims to black. Fixing it means splitting the pass — a coloured wash for the alpha-driven sources, black for `flashBlack` — which is a change to the *fade* path rather than to this one. Left as the next item rather than bundled in.
