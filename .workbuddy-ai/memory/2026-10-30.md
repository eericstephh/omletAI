# 2026-10-30

## Feather gamma shipped (`820a2bb`)

`MaskPostProcess.FEATHER_GAMMA = 1.4f`; `gaussianFeather` now wraps the three
box passes in `blur(m^1.4)^(1/1.4)` via a new `gammaPass`.

- **The 2026-10-26 note was wrong.** It said the gamma was skipped because "its
  direction was never verified (doc §11)". §8.5 of
  `docs/CAPCUT_RE_BACKGROUND_REMOVAL_2026-10-25.md` records the ordering as
  **observed**, and §11 — the explicit "what was NOT confirmed" list — does not
  mention it. The omission was a self-generated hedge. Same failure mode as the
  `audioClips` and `compileDebugUnitTestKotlin` claims: a hedge that hardened
  into a fact because nobody re-read the source.
- Wraps the passes **as a group**, never per pass (that compounds to γ³).
- Safe by construction: the two powers are exact inverses, so a constant field
  survives untouched, and the weighting is the identity when the blur is
  skipped → cannot disturb the `isNoOp` path.
- Effect: on a step edge the result is `Φ^(1/1.4)`, so the 50 % contour moves
  **outward** to ≈ 0.61 with the same reach (~20 % outward bias at feather = 1).
- 6 new tests in `MaskPostProcessTest` (18 total). The strongest one: on a
  *binary* mask the pre-power vanishes (0 and 1 are fixed points), so the result
  must equal `plainBlur^(1/1.4)` to 1e-6 — that pins the formula and the
  once-only application in one assertion.
- `gammaPass` clamps to 0..1 first: `Math.pow` returns NaN for a negative base
  with a fractional exponent, and one NaN would spread across the whole mask
  through the blur's window sums.

## Freeze frame — research done, implementation not started

Media3 1.5.0 verified by `javap` on the real AARs, not from priors:

- `EditedMediaItem.Builder.setDurationUs` exists but is **the wrong API** for
  stills. `DefaultAssetLoaderFactory.createAssetLoader` branches on
  `TransformerUtil.isImage(...)` and throws *"The imageDurationMs field must be
  set on image MediaItems."* → use **`MediaItem.Builder.setImageDurationMs(ms)`**.
- `DefaultAssetLoaderFactory(Context, DecoderFactory, Clock)` (what
  `Transformer.Builder(context)` installs) builds a `DataSourceBitmapLoader`
  itself, so image export needs **no** factory wiring.
- **The preview can render stills with no layout change**: `DefaultRenderersFactory`
  calls `buildImageRenderers` → `ImageRenderer`; `PlayerView` inflates its own
  `exo_player_view.xml`, which already contains `<ImageView android:id="@id/exo_image">`;
  and `PlayerView.setImageDisplayMode(IMAGE_DISPLAY_MODE_FIT|FILL)` exists.
- Design that follows: a freeze is a normal `VideoClip` whose `uri` is a PNG, so
  `durationMs` / trim / speed / `effectiveDurationMs` / timeline layout all work
  unchanged. Mark it with a **derived** predicate (URI suffix `.freeze.png`),
  not a persisted boolean — a boolean has to survive `toVideoProject` (bug class
  1) whereas a URI suffix cannot desync.
- Known follow-ups if it is built: `seedVideoAudioClipsIfNeeded` must skip
  stills (it filters only `!isAudioOnly`, so a PNG would get an AudioClip);
  thumbnails need a `BitmapFactory` path (MediaMetadataRetriever cannot read a
  PNG); the export must skip `SpeedChangeEffect` and the clipping config for
  stills.

## UI budget blocks the obvious entry point

`ContextualToolbarSpecTest` pins `trailing.size <= 2` (clip context is already
Duplicate + Delete) and exact chip counts (17/18). A freeze action therefore
cannot be a trailing action, and adding a chip means editing pinned counts.
`ToolPanel.TRIM` (`TrimPanel`, `EditorScreen.kt:5844`) is the natural home and
costs no toolbar budget.
