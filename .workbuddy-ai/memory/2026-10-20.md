# 2026-10-20 — Persian subtitle accuracy (whisper decode path)

User: «بعضی کلمات فارسی رو اشتباه می‌نویسه … مثلا گفته شده: درآپدیت جدید، ولی زیرنویس نوشته:
در رابطه ایتجایزش». Tested with BOTH whisper models (offline Small + Groq cloud), so the cause is
the shared pipeline, not one model.

## Root causes found (all in the shared path)

1. **`logprob_thold = -0.8` in `whisper-jni.cpp` forced constant temperature fallback.** whisper.cpp's
   retry ladder is t = 0, +inc, … up to 1.0 and **the LAST rung is accepted unconditionally**
   (`if (it != temperatures.size() - 1)` guards the quality test, whisper.cpp:7524). Persian's
   agglutinative BPE gives *correct* sentences avg_logprobs ≈ -0.6…-0.9, so -0.8 pushed ordinary
   windows down the ladder and the accepted subtitle was whatever the 0.8/1.0 decode invented.
   → back to upstream **-1.0**.
2. **`temperature_inc = 0.1` (BALANCED) = eleven rungs.** → all modes now 0.2 (upstream, six rungs).
   Accuracy difference between FAST/BALANCED/ACCURATE is beam width alone (1/5/8).
3. **Both cloud paths sent an instruction prompt** ("قواعد فارسی: کلمات فارسی را شکست ندهید…").
   The API's `prompt` is the same initial_prompt mechanism: the decoder IMITATES it, it does not
   obey it → a ready-made sentence to hallucinate. → `WhisperPrompt.PRIMER` (natural Persian) in
   `GroqWhisperClient.buildPreamble` and `CloudWhisperService`.
4. **No anti-alias filter when decimating 48k→16k.** `AudioExtractor.resampleMonoShortTo16kFloat` did
   bare linear interpolation (-13 dB at source Nyquist), folding 8–24 kHz (hiss, sibilance, music)
   into the speech band. → `AudioResampler.resampleShortMonoToFloat` runs a 4th-order Butterworth LP
   at 45 % of the target rate, streaming (no source-sized float copy).
5. **No level conditioning.** Whisper's log-mel front end has no AGC → quiet phone audio decodes into
   fluent-but-wrong Persian. → `WhisperAudioConditioner` (80 Hz 4th-order HP + active-frame RMS →
   -20 dBFS, boost ≤ +18 dB, robust 99.5-percentile peak guard so one click cannot cancel the boost).
6. **Fixed 30 s window grid** split words in half at every boundary (19 damaged boundaries on a
   10-min video). → `WindowPlanner` cuts in the quietest 10 ms frame within ±600 ms of each mark.
7. **`no_context = true` lost cross-window continuity** (whisper.cpp's own loop feeds `prompt_past`
   forward; we called `whisper_full` per window and threw it away) → `WhisperPrompt.carryOverFrom`
   appends the previous window's tail, gated on mean word confidence ≥ 0.55 so a bad window cannot
   poison the next.

# Round 2 — «هوشمند» tools crashed on tap

User report: "در گزینه هوشمند که ابزارهای هوش مصنوعی رو داره هر کدومشو میزنم کرش میکنه."

## Diagnosis (adb, not guesswork)

`adb logcat -b crash -d` held exactly **two** app tombstones in a week — so the failure was not a
per-panel UI crash (no `!!` / `require(` in any of the 11 AI panels).

1. **SIGABRT, 14:52** — `JNI DETECTED ERROR IN APPLICATION: non-zero capacity for nullptr pointer: 1 in
   call to NewDirectByteBuffer from ImageReader$SurfaceImage.nativeCreatePlanes(int,int,long)`;
   frames `yuv420ToBitmap` ← `imageToBitmap` ← `SequentialFrameSampler.sample` ← `TesseractOcrEngine`.
2. **SIGSEGV, 14:50** — `#00 libGLESv1_CM.so (glGetString+52)` ←
   `upscale.DeviceCapabilityDetector.queryGlesMajor` ← `EsrganUpscalePipeline.run`.

## Root causes

**EOS buffer rendered.** Both hot decode loops called `releaseOutputBuffer(st, true)` for *every* output,
including the `BUFFER_FLAG_END_OF_STREAM` one. An EOS output has no picture, so the reader produced an
`Image` with no gralloc buffer. `getPlanes()` is lazy → the abort landed on `planes[0]`, and CheckJNI
kills the process, so no Kotlin `try/catch` could ever have caught it. `AiExportHooks` and
`OverlayCompositeRenderer` already used `!isEos`; the two loops that crashed did not.

**Image held across the AI work.** `onFrame` is `suspend` and runs inference for seconds against a
**3-slot** reader, so the decoder starved and the driver reclaimed the buffer.

**Blocking acquire.** `acquireNextImage()` blocks when empty — it never returns null. Called unguarded, the
sampler hung at end-of-stream.

**Context-less GL.** `glGetString` on the upscaler worker thread with no current EGL context; `runCatching`
cannot catch a native fault. Replaced with `FeatureManager`-free metadata:
`packageManager.systemAvailableFeatures.maxOfOrNull { it.reqGlEsVersion }`.

## Changes

- `ai/media/SequentialFrameSampler.kt` — `releaseOutputBuffer(st, !eos)`; `pendingImages` counter gates every
  acquire; `Image` closed **before** `onFrame`; bitmap recycled if the callback throws; counter +
  `ptsQueue` re-synced on `IllegalStateException`.
- `ai/media/VideoFramePipeline.kt` (`runLoop`) — same EOS fix, same counter, `Image` closed before
  `req.frameOp.process`, bounded late-image drain. This one path is used by matting bake, upscale, motion
  tracking and reframe, so it explains the breadth of the report.
- `ai/upscale/DeviceCapabilityDetector.kt` — GL probe replaced with `FeatureInfo.reqGlEsVersion`; dropped the
  `android.opengl` import; KDoc corrected (it claimed the GL call was "safe from a background thread").
- NEW `test/ai/AiFrameDecodeLifecycleTest.kt` — 6 source-shape tests pinning all four rules.

## Verification

`compileDebugKotlin` clean. New test 6/6, `AiFrameAccuracyWiringTest` 4/4,
`upscale.DeviceCapabilityDetectorTest` 7/7. Full suite: **3018 tests, 7 failed — all
`WhisperLargeV3LockfileTest`** (stale, asserts a Large-v3 catalog; unrelated, added to the never-chase list).
APK `122,176,275 B`, zipalign OK, debug-signed; DEX grep shows `reqGlEsVersion` in `classes3.dex` and no
`glGetString`/`OpenGL` in any app shard (`classes17.dex` is a third-party GL lib with zero app classes —
a false positive worth remembering).

**Not verified end-to-end on device**: the phone was on the keyguard, so `uiautomator` returned the lock
screen and the tools could not be tapped from here. Installed with `adb install -r` and launched clean
(no crash on start); the user must confirm the taps.

## Memory hygiene

`MEMORY.md` had exceeded the injection limit and was being truncated. Split the procedural bulk into
`reference/build-and-apk.md` and `reference/ai-media-decode.md`, leaving pointers. 10,711 → 9,608 chars.

# Round 3 — «حذف» was video-only

User report: "قابلیت دکمه حذف فقط برای تایم لاین ویدیو فعاله برای صدا فعال نیس."

## Diagnosis

Two independent holes, both structural:

1. `ContextualToolbarSpec.trailingActionsFor(AUDIO_SELECTED)` returned **`emptyList()`** — the audio
   context rendered no delete button at all. A test asserted exactly that
   (`root and audio have no trailing actions`), i.e. the suite pinned the defect as if it were the contract.
2. The `"delete"` branch in `EditorScreen` read only `uiState.selectedClipId`. `selectAudioClip` **clears**
   `selectedClipId` (one selection at a time), so even if a button had existed it was a guaranteed no-op
   while audio was selected.

There was also no `deleteAudioClip` in the ViewModel — `splitClip`/`deleteClip` are `project.clips`-only.

## The trap that shaped the design

`seedVideoAudioClipsIfNeeded` rebuilds a paired `AudioClip` for **every video clip that has none**, on every
project load. So "delete the Video Audio tile" cannot stick: the row comes back next time the project opens,
and the exporter re-extracts that soundtrack from the video source regardless. Muting the owner clip in the
same step does not save it either — the tile still returns.

Rejected alternative: skip seeding when `volume <= 0f`. It would make a normal mute (the Volume slider
reaches 0, and `toggleMuteForSelectedClip` uses exactly that) destroy the tile's fades / beat data / cached
PCM on the next reload. Data loss for a mute toggle — no.

Proper fix would be a persisted `detached` flag on `VideoClip`, which means the whole per-clip chain (model +
`EditorStateJson` + `RoomProjectRepository.toVideoProject` + `toClipAiTools` + `RenderSegment`) — not
justified by one button. Recorded as an open follow-up.

## Changes

- `ContextualToolbarSpec` — new `DeleteAudioAction` (id `del_audio`, actionId **`delete`** shared with
  `DeleteClipAction`, following the `audio_split`/`clip_split` precedent: distinct id for the highlight,
  shared actionId for the dock's single `when`); `trailingActionsFor(AUDIO_SELECTED)` now returns it.
- `EditorViewModel.deleteAudioClip(id): AudioDeleteOutcome` — new top-level enum
  `AudioDeleteOutcome { Deleted, NotFound, PairedAudio }` (a boolean conflated "stale id" with "needs an
  explanation"). Standalone audio → removed from `project.audioClips`, selection + panel cleared,
  `persistProjectMeta()`. Paired audio → **refused before any mutation or history push**.
- `EditorViewModel.notifyPairedAudioNotDeletable()` — `editorNotice`, the same banner mechanism as
  `notifyLastClipDeleteRefused` / `notifySplitNotPossible`. A refused delete must say why.
- `EditorScreen` — the `"delete"` branch checks `selectedAudioClipId` **first**, then falls back to the clip.

## Tests

trailing delete action` + `root has no trailing actions` + a shared-actionId assertion),
`AudioLaneLifecycleWiringTest` 9 (+4: standalone removal, paired refusal, refusal-before-mutation ordering,
notice wiring). Full suite **3024 tests, 7 failed — all the known stale `WhisperLargeV3LockfileTest`**.

## Still open on the audio lane (not requested)

# Round 4 — drag-to-move on the timeline (audio + video)

Request: «قابلیت جا به جایی با درگ کردن توی تایم لاین اضافه کن هم صدا هم تصویر».

## What was actually missing

Video drag already existed (`ClipBlock` body drag → `onMove(deltaMs)` → `updateClipPosition`). Two real
gaps: the audio lane's tiles had **only** `clickable` (no gesture at all), and `ClipBlock`'s gesture read a
**frozen** `onMove` — its `pointerInput(label)` key never changes during a drag, and `onMove` closes over
the clip's start, so the incremental delta resolved to `originalStart + oneFrame` (visible jitter).

## Design decision that mattered — DELTA, not absolute

`moveAudioClip(id, deltaMs)` takes a **delta** and resolves it against live ViewModel state. Passing an
absolute `startMs + delta` computed in the gesture is wrong for the same stale-closure reason: `startMs` is
frozen inside `pointerInput(audio.id)`. This is deliberately different from `onClipMoved`, which takes an
absolute position because its caller reads live state. The tile's gesture re-anchors `dragStartX` on every
event, so each callback carries an incremental delta — that is what makes "live start + delta" correct
rather than double-counting. **If you ever change one of those two, change both.**

## Undo latch (found while verifying, pre-existing for video)

`lastDraggedClipId` / `lastDraggedAudioId` were set on the first drag frame and **never cleared** —
`lastTrimmedClipId` always had `onClipTrimEnd`. Consequence: drag → undo → drag the same object skipped
`historyDelegate.push()`, so the second move was not undoable at all. Fixed for both lanes by routing every
lane's drag state through one lambda in `EditorTimeline`:

```kotlin
val setDraggingClip: (Boolean) -> Unit = { dragging ->
    isDraggingClip = dragging
    if (!dragging) onDragEnd()
}
```

`EditorTimeline` gained `onDragEnd: () -> Unit = {}`; `EditorScreen` passes a lambda clearing **both**
latches. Note `ClipBlock` calls `onDragStateChange(false)` unconditionally at gesture end (so a plain tap
also fires it — harmless, null→null).

## Changes

- `EditorTimeline` — `onAudioClipMoved`, `onDragEnd`; `AudioLaneRow` gained `onAudioClipMoved` +
  `onAudioClipDragStateChange` and a `pointerInput(audio.id, pixelsPerMs)` `awaitEachGesture` on the tile:
  nothing consumed until `touchSlopPx`, vertical-dominant swipes yield to the lane stack, `change.consume()`
  only while dragging so `clickable` still selects. `ClipBlock` hardened with `rememberUpdatedState` for
  `onMove` / `onTrim` / `onDragStateChange` / `onGestureEnd`.
- `EditorViewModel.moveAudioClip(id, deltaMs, pushHistory)` — paired audio **delegates to
  `updateClipPosition(ownerId, …)`** (which already shifts the paired `AudioClip` and persists both tables);
  standalone audio moves `startTimeMs` itself and calls `persistProjectMeta()`.
- `EditorScreen` / `EditorTimelineSection` — `onDragEnd`, latch reset, `lastDraggedAudioId` latch.
