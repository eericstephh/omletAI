# 2026-10-14

## Device diagnostic report → play-button root cause (audio chain lane)

User installed `dist/Omelet-1.4.0-debug-playback-diagnostics.apk` and shared the
diagnostics panel output — it WORKED (7 events captured). Two findings:

1. `ai_subtitle/generation_model_failed` with `model=CLOUD_API`: no Groq key saved.
   Not a bug — the message is actionable (Settings ← AI connection, or offline Whisper).
2. **Five repeated `editor/player_error` warnings**:
   `MediaCodecAudioRenderer error, index=1, format=Format(2, null, null, audio/raw, null, -1, und, ..., [2, 48000]), format_supported=YES`

### Root cause — verified from the Media3 1.5.0 bytecode, not guessed

`javap -c` on the cached `media3-exoplayer`/`media3-common` classes:

- `SonicAudioProcessor.configure` **throws `UnhandledAudioFormatException` unless
  input encoding == `ENCODING_PCM_16BIT`** (constant 2) — everything else throws.
- `DefaultAudioSink.configure(Format,...)` builds the pipeline as
  `[ChannelMapping, Trimming, ToInt16] ++ [custom chain...]` for a 16-bit decoder
  output; `shouldUseFloatOutput` only turns on for **high-resolution** PCM
  (24-bit int / 32-bit float), so no `ToFloat` stage precedes custom processors
  for ordinary media. **Media3 inserts NO converters between custom processors**
  — its float/int converters sit at the head of the pipeline only.
- `AudioProcessingPipeline` is a plain chain with no inserted conversions.
- `DefaultAudioProcessorChain(custom...)` = `[custom..., silenceSkip, sonic]`.

`VoiceEffectAudioProcessor` (shipped 2026-10-13 with the voice changer) declared
**`ENCODING_PCM_FLOAT` output** on the false assumption that "Media3 inserts its
own converters ahead of us for a 16-bit source". The preview chain
`[VoiceEffectAudioProcessor, SonicAudioProcessor(pitch)]` therefore hit
`Sonic.configure(FLOAT)` → `UnhandledAudioFormatException` →
`AudioSink.ConfigurationException` → the exact renderer error above, on **every
play attempt**. The JVM suite could not catch it: the DSP tests are pure maths;
only the device exercises the chain. Same chain shape exists in the export.

### Fix

`VoiceEffectAudioProcessor` now declares **PCM_16BIT output always** and reads
either input encoding (float → `/32768f`; 16-bit → `asShortBuffer()/32768f`),
converting back with Media3's own constant `clamp(x,-1,1) * 32767f` (read from
`ToInt16PcmAudioProcessor.queueInput`). Identity profile on a 16-bit stream is a
**verbatim byte copy** (bit-exact, no DSP round-trip). Updated the two false KDocs
(`VoiceEffectAudioProcessor`, `VoiceEffectPreviewAudio`), repointed
`VoiceEffectWiringTest`'s "processor outputs float pcm" test at the 16-bit lane,
and added `VoiceEffectAudioProcessorTest` (7 JVM tests: lane declarations, verbatim
identity passthrough, Media3 conversion constants, active-effect lane/finite,
live profile retargeting). Also included `errorCodeName` in the forwarded
`onPlayerError` message — the panel previously lost the error code, so a device
report could not name the failing stage.
