## Found on device — P0: export fails for any clip with speed ≠ 1

```
Export failed (code 6001) at TRANSFORMER:
Audio error: Error while registering input 0,
audioFormat=AudioFormat[sampleRate=44100, channelCount=2, encoding=4]
  caused by UnhandledAudioFormatException
```

`encoding=4` is `ENCODING_PCM_FLOAT`. Verified by `javap` on the real AARs:

- `SonicAudioProcessor.configure` compares the encoding against the constant `2`
  (`ENCODING_PCM_16BIT`) and throws otherwise.
- Media3's `AudioGraph` hands each item's chain the format it mixes in — float — once the
  composition holds more than one audio sequence.
- `ToInt16PcmAudioProcessor` exists in media3-common 1.5.0 and accepts float *and* 16-bit.

So at 1× no Sonic stage is in the chain and nothing rejects the float buffer; adding the
speed stage is what exposed it. This had never been exercised on a device.

Fix attempted: `buildAudioProcessors` now computes `needsSonic` (pitch stage, speed curve, or
constant speed) and, when true, puts `ToInt16PcmAudioProcessor()` at the **head** of the
chain — ahead of `VolumeScalingAudioProcessor` and the voice stage as well, because those
read `ShortArray` too. Pinned by `AudioChainFormatTest` (3 tests, source-shape,
CRLF-normalised).

**The fix is necessary but NOT sufficient — the bug is still open.** Rebuilt, reinstalled,
re-exported at 2×: same failure, same `encoding=4`, on the shipped build. The percentage
the UI showed when it failed (5 %, then 31 %, then 91 %) is polling lag, not a different
stage — it is always the audio-registration step at the end of the video pass.

What that rules out and what it leaves:

- Ruled out: the rejection is not from the per-item chain of the video clip — that chain
  now ends in 16-bit, so a processor downstream of our converter cannot have seen float.
- `UnhandledAudioFormatException` carries the format the *rejecting* processor saw, so the
  throw is somewhere the buffer is still float.
- Leading hypothesis: a **second** `AudioGraphInput` is registered for an
  `EditedMediaItem` that carries no audio processors at all (the paired-audio lane, or a
  sequence built outside `buildAudioProcessors`), so nothing converts its float buffer
  before a Sonic stage downstream.

Next step needs a **debug** build: the release build logs nothing from Media3
(`logcat` had zero `AudioGraph` / `UnhandledAudioFormat` lines across 400 k lines), so the
full `ExportException` cause chain has to come from a debuggable install or from a
temporary `Log.e` around the Transformer listener.

Speed was reset to 1.0× afterwards so the project exports again.

# 2026-10-31 (later) — P0 RESOLVED: the audio chain declared the wrong format

The `encoding=4` export failure is solved, and the cause was our own code, not Media3.

## How it was found

`android.util.Log` never reaches logcat for this app on MIUI, and
`getExternalFilesDir(null)` returns a path the app cannot create on this device
(`/storage/emulated/0/Android/data/com.aicreatorstudio.app/` genuinely does not exist,
and `Android/data` is unreadable from the shell on Android 11+ anyway). So
`ExportDiagnostics` now also writes to **MediaStore Downloads**, which `adb exec-out cat`
can read on a release build with no root:

```
adb exec-out cat /storage/emulated/0/Download/export-failure.txt
```

The report carries the message, the cause chain, a per-segment **audio chain audit**
(`ExportDiagnostics.noteChain`) and the full stack. That audit is what cracked it.

## The bug

The chain log said:

```
clip=matting-….mp4 speed=2.0 curve=false volume=0.39 voiceIdentity=true fade=0/0
  -> ToInt16PcmAudioProcessor,VolumeScalingAudioProcessor,SpeedChangingAudioProcessor
```

The converter was there, first — and the throw was still `SonicAudioProcessor.configure`
on float. Because `VolumeScalingAudioProcessor.onConfigure` **hard-codes
`C.ENCODING_PCM_FLOAT` as its output** and reads the buffer with `asFloatBuffer()`.
`FadeAudioProcessor` does the same. So the chain converted float→16-bit and then
immediately re-declared float, and the Sonic stage behind it got float.

`AudioProcessingPipeline.configure` chains each processor's *returned* format into the
next one and only advances when `isActive()`. A processor that lies about its output
format silently poisons everything downstream.

At 1× there is no Sonic stage, so nothing noticed. Adding the speed stage is what
exposed it — and it also means the volume stage would have read 16-bit data as floats
if it ever had been fed 16-bit.

## The fix

Ordering, not another converter:

```
[Volume(float), Voice DSP(float)] -> ToInt16 -> [pitch Sonic, SpeedChanging]
  -> ToFloat (only if a fade follows) -> [Fade(float)] -> ToInt16 (always, tail)
```

- The float-only stages never cross the conversion.
- **Every chain must END in 16-bit.** Media3 takes the *mixer* format from input 0's
  output and then requires every later input to match it, and it appends its own
  `SonicAudioProcessor` / `ChannelMixingAudioProcessor` (both 16-bit-only) to every
  input after the first. A chain ending in float poisons the mixer and breaks input 1.
- `ToFloatPcmAudioProcessor` is hand-written: media3-common 1.5.0 ships
  `ToInt16PcmAudioProcessor` and no float counterpart. It mirrors `ToInt16`'s contract —
  returns `AudioFormat.NOT_SET` for float input, so it is inactive and free.

`AudioChainFormatTest` was rewritten to pin the new order (5 tests, passing). Its old
version asserted the converter was at the head, i.e. it was pinning the wrong invariant.

## Device results — crash fixed, but a NEW audio defect surfaced

Three exports of the same project, measured by parsing `stts`/`mdhd` out of the
pulled MP4 (`.dexwork/mp4stts.py`, `.dexwork/mp4dur.py`):

| speed | video | audio | audio ÷ video |
|-------|-------|-------|---------------|
| 1× (control, pre-fix build) | 35.800 s | 35.805 s | 1.00 |
| 1.5× | 23.867 s | 12.005 s | 0.50 |
| 2×   | 17.900 s | 9.033 s  | 0.50 |

- **The `encoding=4` crash is gone.** Both 1.5× and 2× now export to completion and
  write no failure report. `export-failure.txt` is written only on failure, so its
  absence is the evidence.
- **New bug: at any speed ≠ 1 the audio track is exactly HALF the video duration.**
  It is not "speed squared" — the factor is a constant 2 at both 1.5× and 2×, so it
  is not the speed arithmetic at all.

What that constant-2 rules in/out:

- It only appears when a Sonic stage exists, i.e. exactly when the chain gains the
  `ToInt16PcmAudioProcessor` conversion. At 1× the chain is float-only and correct.
- `SpeedChangeEffect.getDurationAfterEffectApplied` makes Media3 retime the *item*
  to `source/speed`; `AudioGraphInput.currentItemExpectedInputDurationUs` follows it.
  Our `SpeedChangingAudioProcessor` then applies the speed a second time — but that
  would scale with speed, and the measurement says it does not.
- So the remaining suspect is the float↔16-bit conversion: something derives the
  audio sample count from **bytes** using the decoder's 4-byte float frame size
  while the chain now emits 2-byte frames, which halves the duration exactly.

Next experiment that would settle it (not yet run): force `hasSonic` at speed 1 by
adding only a **voice pitch** stage. Video stays 35.8 s (no `SpeedChangeEffect`), so
if audio comes out 17.9 s the conversion is the culprit; if it stays 35.8 s the
constant 2 comes from the speed path instead.

Until this is fixed, **speed ≠ 1 produces a file whose audio stops halfway** — worse
than the crash in one way, because it fails silently instead of showing an error.
