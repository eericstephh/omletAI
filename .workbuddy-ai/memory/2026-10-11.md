# 2026-10-11 — Offline Persian subtitle correction upgrade

## What was asked
Strengthen the existing offline Persian correction layer: contextual
ASR fixes (e.g. «آشق» → «عاشق») with sentence evidence only, strict
preservation of colloquial/names/numbers/timestamps, no network, no
LLM, no runtime model download, tests + debug build.

## Audit findings (the layer already existed — do not rebuild)
- `ai/subtitle/PersianNormalizer.kt` — 1:1 char fold فقط (ي→ی، ك→ک،
  strips BOM/ZWSP, preserves ZWNJ). Per-word so timings survive.
- `ai/subtitle/corrector/` — already a 5-stage pipeline:
  `PersianLexicon` (lexicon + `ZWNJ_FIXES` map, 84 entries) →
  `SuspiciousWordDetector` (rules A/B/C) → `CorrectionCandidateGenerator`
  (collapse/strip/mi-prefix/edit-distance) → `ContextValidator`
  (`OfflineContextValidator`, weighted selector, interface is
  model-agnostic) → `TranscriptCorrector` (apply/flag/keep + JSON log).
- Called once: `EditorViewModel:3500` → `SubtitlePostProcessor.postProcess`.
- Settings live in `SubtitlePostProcessSettings` (autoApply 0.90 /
  review 0.70, `correctTypos` default true).
- The corrector had **no vocabulary for sound-alike errors at all** —
  that was the real gap, not a missing pipeline.

## What I added
1. `corrector/PersianConfusables.kt` (new) — character-level sound
   groups (`عآاأإ`, `سصث`, `زذضظ`, `تط`, `حه`, `قغخ`, `کگ`) plus a
   separate 1:2 `EXPANSIONS` map (`آ`→`عا`). Derives variants by
   re-spelling; a variant only becomes a candidate if the lexicon
   already has it. **No word pair is hardcoded** — «آشق»→«عاشق» falls
   out of `آ`→`عا` × lexicon hit.
2. `corrector/HomophonePolicy.kt` (new) — a **veto** gate run before
   candidate generation: user dict, non-Persian/numeric, already-a-lexicon-word,
   trailing-doubled-letter (structural → outranks colloquial),
   deliberate repetition, colloquial register, no lexical neighbour.
3. `SuspiciousWordDetector` — new rule D `REASON_HOMOPHONE`
   (confidence-gated: only fires when whisper conf < 0.60 or null).
4. `CorrectionCandidateGenerator` — new origin
   `ORIGIN_HOMOPHONE = "confusable_rewrite"`, derived from the map.
5. `ContextValidator` — homophone candidates get **no** mechanical
   bonus; `+0.12` only if `contextSupportsNoun(prev)` (noun-slot
   markers: یه/یک/این/اون/مثل/دوست…), else `−0.30`. Without evidence
   they cannot reach 0.90.

## Bugs I hit and fixed (worth remembering)
- **Kotlin list-type trap.** `m[c].orEmpty() + group.filter { it != c }`
  mixes `List<String>` with `List<Char>` → infers `List<Any>` and the
  whole group string leaks in as one "replacement"
  (`MEMBERS['آ'] == ["عاأإ","عا","ا"]`). Fix: `.map { it.toString() }`.
- **`آ` is U+0622, NOT U+0627.** My glottal group originally listed
  plain `ا`; `آ` was silently absent. Both must be listed.
- **The veto over-reached.** Matching colloquial markers as
  *substrings* (`"م"` inside `هستمم`) blocked the mechanical
  corrections that already worked. Structural defects must short-circuit
  the policy before any register heuristic.
- `"میرم" → "میرم"` is **pre-existing intended ZWNJ behaviour**
  (in `ZWNJ_FIXES`), not a register change. Test expectation was wrong,
  not the code.

# 2026-10-11 (fourth task) — export stuck at 88% (the real root cause)

## Root cause — PROVEN from Media3 1.5.0 bytecode, not guessed
`javap -p -c` on `Transformer`, `TransformerInternal`, `SequenceAssetLoader`,
`ExoPlayerAssetLoader` inside `media3-transformer-1.5.0-runtime.jar`:

1. Media3 progress is a **playback-position ratio**, never an encoder signal:
   `min(player.getCurrentPosition() * 100 / player.getDuration(), 99)`.
2. `TransformerInternal.updateProgressInternal` **averages over ALL sequences**
   (`idiv`). A video+audio composition therefore **cannot** reach 99 — it
   plateaus in the high 80s. That is the observed ~88%.
3. `updateProgressInternal` has **exactly one caller**: `drainExportersInternal()`.
   Once the last sample drains, progress stops being written at all.
4. `endInternal` **RESETS `progressState`/`progressValue` to 0** and then runs
   `MuxerWrapper.finishWritingAndMaybeRelease(...)` — the muxer flush + file
   close — with **zero progress reporting**.
5. The old `pollProgress` loop spun forever waiting for a value the library
   never emits. `grep -E 'withTimeout|timeout|deadline' export/*.kt` → **0 hits**.
   ⇒ infinite hang, no terminal state, UI frozen at 88%.

## Fix (smallest reliable change — export pipeline NOT rewritten)
- `export/ExportConfig.kt`: added pure, JVM-testable `ExportStallPolicy`
  (BASE 120s / FINALIZE 300s / boundary 0.85f) + `ExportStallDetector.check()`
  + `messageFor()`. `ExportStage.FINALIZING` already existed.
- `export/VideoExportEngine.kt`:
  - `pollProgress` rewritten to time **the last progress CHANGE**, not total
    duration — a genuinely slow 4K export is never killed, a true hang fails
    loudly. Emits `FINALIZING` (0.99f) once past the boundary instead of
    sitting on a frozen "Encoding" label.
  - `emitTerminal()` compare-and-set latch — exactly **one** terminal state can
    ever be published. Before, `onCompleted` / `onError` / the watchdog /
    `cancel()` all wrote straight to `activeState`, so a `Failed(stall)` could
    be overwritten by a `Succeeded` = **false success**.
  - `ExportDiagnostics` — metadata only (stage, elapsed, bytes, errorCodeName).
    Explicitly logs **no** media content, no paths, no URIs, no keys.
- `ui/screens/editor/ExportDialog.kt`: `stageLabel()` maps the stage to Persian
  (`"در حال نهایی‌سازی فایل…"`), replacing the raw English `displayName`.

## Verification
- **2187 tests, 2 failed, 2 skipped** (2157 → exactly +30). The 2 failures are
  the same pre-existing asset pair. 168 test classes.
- New: `ExportStallDetectorTest` (17) + `ExportStateTerminalTest` (13) — all green.
  One test was **wrong, not the code**: my detector fires *inclusive* at the
  limit (`silentMs < limit`), the test asserted exclusive. Fixed the test —

- **No device/emulator export was performed.** `Transformer` needs real

  not "verified fixed on a real device".

## Proven by binary analysis (not speculation)
- Shipped `libwhisper.so` (in `build/whisper-audit/`): ELF64 `ET_DYN`,

  ⇒ "unsupported CPU instruction" ruled out.

## Real defects found + fixed (these are the substance)
1. **7.2 MB size-gate hole.** `CatalogEntry.minSizeBytes = 480_000_000` but the
   real `ggml-small.bin` is **487,601,967**. A download truncated inside that
   band passed. Fix: `AiModels.expectedSizeFor()` reads `sizeBytes` from
   `assets/ai-models/manifest.json` (verified present for whisper-small) and
   gates **before** the `.sha256` sidecar is trusted.
2. **Non-atomic install + premature sidecar.** `renameTo` can fail
   cross-filesystem → `copyTo` fallback is not atomic; the SHA check ran on the
   *staging* file, and the sidecar was written regardless → a truncated file at
   the final path looked "installed forever." Fix: post-move **destination**
   re-verification + sidecar written only after it lands intact + backup/restore
   (`<name>.bak`) so a failed repair never costs a working model.
3. **Five faults collapsed into one message.** Added
   `WhisperDiagnostics.Stage` (9 stages) + `WhisperFailure(stage,…)` (a plain
   `Exception` subclass so no `catch (e: Exception)` site changes) +
   `WhisperNative.InitResult` (`Ok`/`LibraryUnavailable`/`NativeReturnedNull`/
   `Threw`) + `initFromFileDetailed()`. In `ensureNativeContext` the file is
   inspected **before** native init; `NativeReturnedNull` is disambiguated by
   exact size — size-correct ⇒ `NATIVE_INIT_NULL` (memory path), size-wrong ⇒
   `MODEL_SHA_MISMATCH`. ⚠️ The `catch (e: WhisperFailure)` arm **must precede**
   `catch (e: Exception)` (Kotlin takes the first match).
4. **39 user-facing Persian literals corrupted to ASCII `?`** at write time
   (EditorViewModel AI-tool status + subtitle msgs, CloudWhisperService 13
   network msgs). Moved to `model/SubtitleMessages.kt` (+ nested `AiTool`
   object). **This had already bitten once** (`SUBTITLE_NO_SOURCE_MESSAGE_FA`).
   Guarded by `assertNoMojibake()` + a repo-wide scan test.
