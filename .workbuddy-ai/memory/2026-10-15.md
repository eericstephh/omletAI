# 2026-10-15 — device report #2: AI tool failures (matting 403, autoframe ABI, motiontrack unknown)

User pasted a second Omelet diagnostic report (`events: total=5 error=4`), all in `ai_tool`.
Playback errors from the previous report are **gone** — the 16-bit PCM lane fix holds.

## 1. `motiontrack` — engine existed but was never registered (wiring, not missing code)

- The toolbar chip (`EditorScreen.kt:5836`) calls `onRunAiTool("motiontrack", opts)` and
  `MotionTrackingEngine.kt` ships `TOOL_ID = "motiontrack"`, but
  `AppModule.provideAiToolEngines` returned
  `listOf(matting, autoFrame, voiceClean, ocr)` — motiontrack absent → `byId()` null →
  `unknown_tool` logged, run fails before any work.
- **Invariant**: `AiToolRegistry` resolves *by id from the Hilt provider list*. Compiler sees
  the class and the call site, neither is wrong. Fixed by adding the engine to the list.
- ⚠️ `SpectralGateVoiceClean` is a second `AiToolEngine` with id `voiceclean` that is
  deliberately NOT registered (the RNNoise engine embeds it as its fallback). A test that
  asserts "every engine class in `ai/engines/` is in the provider" would flag it — the
  shipped `RegistryWiringTest` maps *tool ids the toolbar runs* instead.

## 2. `autoframe` — "your processor is not supported" on a supported arm64 device

- Verified chain (bytecode + APK + Gradle cache, no guessing):
  - probe did `System.loadLibrary("mediapipe_tasks_vision_jni")` in **both**
    `SaliencyTrackerEngine` and `MediaPipeMattingEngine`;
  - the resolved `tasks-vision 0.10.35` AAR ships **no `.so` at all**;
  - the only native lib in the APK is tasks-core's `lib/arm64-v8a/libmediapipe_tasks_jni.so`;
  - probe fails → `classify(..., libraryAvailable = false)` → `LIBRARY_ABI_MISSING` → the
    Persian "این نسخه … برای پردازندهٔ این دستگاه ساخته نشده است" sentence, on hardware the
    APK fully supports.
- Old (0.10.14/0.10.21) tasks-vision AARs did ship `libmediapipe_tasks_vision_jni.so`, so
  the probe was right once and drifted when the dependency moved.
- Fix: new `ai/MediaPipeNativeLib.kt` — one process-wide probe with a **candidate list**
  (`mediapipe_tasks_jni` first, legacy name second), shared by both engines; per-engine
  copy + fields deleted. `lastLoadError` is exposed for `NativeEngineFailure.classify`.

## 3. `matting` — HTTP 403 from storage.googleapis.com (the model was never bundled)

- `models.lock.json` had `selfie_multiclass: "bundled": false` (drifted; its own `_comment`
  still said "bundled (16 MB)"), so the APK contains no selfie asset — the install always
  took the network path, and the Google host answers 403 on the user's network
  (same URL returns 200 from here).
- Fix: downloaded the artifact and **verified byte-exact** — 16,371,837 bytes,
  sha256 `c6748b1253a99067ef71f7e26ca71096cd449baefa8f101900ea23016507e0e0` (lock's) —
  into `app/src/main/assets/ai-models/selfie_multiclass/`, and flipped `bundled: true`.
  Bundled path is offline; the URL stays as the repair fallback.
